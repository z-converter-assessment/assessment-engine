# ZConverter Assessment 발표 대본

## 1. ZConverter Assessment

안녕하세요. 저희 2팀은 "고객 내부망 서버의 데이터"를 수집하고, 이를 "운영과 클라우드 이전, 재해복구 의사결정"에 활용할 수 있는 정보로 만드는 "ZConverter Assessment"를 구축했습니다.

오늘은 이 시스템이 "왜 필요한지"와 사용자가 "어떤 방식으로 활용할 수 있는지"를 중심으로 말씀드리겠습니다.

## 2. 배경과 프로젝트 정의

먼저 "현재 환경 정보"가 왜 필요한지와 어떤 "의사결정 정보"가 부족한지 살펴보겠습니다. 이어서 이를 바탕으로 세운 "프로젝트의 목표"와 "제품의 역할"을 설명하겠습니다.

## 3. 기업 연계 과제의 출발점

"고객 내부망"에는 운영체제와 자원 구성이 서로 다른 서버가 함께 운영됩니다.

이 서버들을 클라우드로 이전하거나 재해복구 환경에서 다시 구성하려면 "현재 환경 파악"이 먼저 필요합니다. 각 서버의 "자원 구성", "실제 사용량", "실행 서비스"를 함께 확인해야 의사결정에 사용할 수 있는 현재 상태가 됩니다.

이 정보를 바탕으로 "새 VM"에 필요한 CPU, 메모리, 스토리지 사양을 정합니다. 그래야 성능 부족과 불필요한 자원 할당을 함께 줄일 수 있습니다.

서버 정보와 실제 사용량을 함께 파악해 클라우드 이전과 재해복구 사양의 근거를 만드는 것이 이 기업 연계 과제의 출발점입니다.

## 4. 의사결정 정보의 공백

자사는 고객사 내부망을 조사한 결과를 "Excel"로 정리했습니다. 이 자료로 서버의 기본 구성은 파악할 수 있지만, 실제 사용량과 시간에 따른 변화까지 확인하기는 어렵습니다. 이 한계를 보완하려면 현재 환경에서 3가지 정보를 함께 확인해야 합니다.

첫째는 "자원 구성"입니다. 운영체제(OS), 중앙처리장치(CPU), 메모리, 스토리지와 네트워크의 현재 구성을 확인합니다. 둘째는 "실제 사용량"입니다. 평균과 피크 사용량, 자원별 병목을 봅니다. 셋째는 "변화 추세"입니다. 용량 소진, 사용량 상승, 반복되는 포화를 확인합니다.

이 정보가 없으면 새 VM 사양 판단이 왜곡됩니다. "과소 할당"은 성능 저하와 중단 위험을 만들고, "과다 할당"은 사용하지 않는 자원의 지속 비용을 만듭니다.

## 5. 프로젝트의 목표

앞에서 말씀드린 판단 오류를 줄이기 위해, "현재 환경 정보"를 원하는 범위와 수신자에 맞는 평가 결과로 제공한다는 프로젝트 목표를 세웠습니다.

현재 환경에서 수집하는 사실은 "자원 구성", "실제 사용량", "변화 추세"입니다.

같은 정보를 "환경 전체", "선택한 서버 묶음", "개별 서버" 단위로 제공합니다. 결과의 깊이도 수신자에 맞춥니다. "고객"에게는 결론과 조치를, "엔지니어"에게는 판단 근거와 세부 진단을 제공합니다.

## 6. ZConverter Assessment

이제 이 목표를 구현한 "ZConverter Assessment"의 전체 흐름을 보겠습니다. 핵심 흐름은 3단계입니다.

첫째는 "현재 환경 정보 전달"입니다. 모니터링 Agent가 고객 내부망 서버의 인벤토리와 측정값을 수집 백엔드 서버로 전달합니다.

둘째는 "규칙 기반 평가"입니다. 수집 백엔드 서버가 전달받은 데이터를 공통 규칙으로 분류하고 자원 적정성과 운영 신호를 평가합니다.

셋째는 "결과 전달"입니다. Web Dashboard로 현황을 확인하고, Report로 결과를 공유하며, Assessment API(Application Programming Interface)와 JSON(JavaScript Object Notation) Export로 Terraform 같은 자동화 도구와 연계합니다.

모든 결과 전달 수단이 "같은 수집 정보와 평가 규칙"을 사용하므로 판단 기준이 일치합니다.

## 7. Assessment 아키텍처

전체 시스템은 고객 내부망 안의 "수집 대상 서버군"과 "수집 백엔드 서버", 2개 영역으로 구성됩니다.

수집 대상 서버군의 각 서버에는 "Monitoring Agent"가 설치됩니다. Agent는 인벤토리와 측정값을 AMQP(Advanced Message Queuing Protocol) 메시지로 발행하고, 모든 메시지는 수집 백엔드 서버의 "RabbitMQ"로 전달됩니다.

수집 백엔드 서버의 "Assessment Engine"은 6개 구성요소로 나뉩니다. RabbitMQ, Consumer, TimescaleDB, FastAPI, Worker, Redis입니다.

수집 및 저장 경로는 "RabbitMQ -> Consumer -> TimescaleDB"입니다. RabbitMQ가 메시지를 받아 전달하고, Consumer가 스키마를 검증해 저장하며, TimescaleDB가 시계열 데이터를 보관합니다.

결과 제공 경로는 "TimescaleDB -> FastAPI -> Web / REST API"입니다. FastAPI가 저장된 정보와 평가 결과를 Web과 REST(Representational State Transfer) API로 제공합니다. Worker는 보고서 생성과 설치 작업의 시간 초과 처리를 담당하고, Redis는 캐시와 온라인 상태 같은 보조 정보를 관리합니다.

## 8. Assessment 기능

Assessment 기능은 "현재 환경 수집 및 평가"와 "평가 결과 활용", 2개 영역으로 나뉩니다.

주 기능의 첫 단계는 "현재 환경 정보 수집"입니다. Monitoring Agent가 서버의 인벤토리와 실제 사용량을 지속적으로 수집합니다. 둘째는 "시계열 저장"입니다. 수집한 데이터를 시간 순서로 누적해 피크와 변화 추세를 확인합니다. 셋째는 "자원 적정성 평가"입니다. 공통 규칙을 모든 서버에 적용해 자원 상태와 권고를 도출합니다.

수집 정보와 평가 결과는 4가지 방식으로 활용합니다. "현황 탐색과 서비스 분류"는 Web Dashboard와 Service catalog에서 제공합니다. "결과 공유"는 Customer Report와 Engineer Report로 제공합니다. "외부 연계"는 Assessment API와 JSON Export로 제공합니다. "자사 솔루션 적용 지원"은 여러 자사 솔루션을 서버에 적용하는 매개체인 ZDM을 설치하고, 서버별 결과를 추적합니다.

## 9. 현장 조건과 검증

제품의 구조와 기능을 설명했으니, 이제 "현장 조건"을 반영한 환경에서 배포와 수집 경로를 검증한 과정을 말씀드리겠습니다.

현장에서 예상한 조건을 정리한 뒤, OpenStack에 "검증 환경과 접근 경로"를 구성했습니다. 혼합 운영체제 서버에 Agent와 Engine을 배포하고, Agent가 발행한 현재 환경 정보가 RabbitMQ와 Consumer를 거쳐 TimescaleDB에 저장되는지 확인했습니다. 같은 검증을 반복할 수 있도록 "환경 재현" 절차도 구성했습니다.

## 10. 현장 조건

현장 검증을 계획할 때 "확정된 조건"과 "현장 확인 사항"을 2개씩 구분했습니다.

"확정된 조건"의 첫째는 "OS coverage", 즉 운영체제 지원 범위입니다. Linux는 CentOS와 RHEL 6 계열부터 최신 배포판까지, Windows는 Server 2003 SP1부터 최신 버전까지 지원해야 합니다. 둘째는 "Native Agent"입니다. Linux와 Windows용 C 기반 바이너리 2종을 제공하고, 각 서버에서 해당 바이너리를 직접 실행합니다.

"현장 확인 사항"의 첫째는 "내부망 인프라"입니다. 물리 환경인지, 퍼블릭 클라우드인지, OpenStack 같은 프라이빗 클라우드인지 사전에 알 수 없습니다. 둘째는 "접근 가능 여부"입니다. 인터넷 연결과 SSH(Secure Shell) 접근 가능 여부가 현장마다 다릅니다.

따라서 Agent 배포 방식은 하나로 고정하지 않았습니다. 내부망 플랫폼과 인터넷 및 SSH 접근 조건을 확인한 뒤, 가능한 배포 경로를 선택하도록 했습니다.

## 11. 검증 환경 구성

검증 환경은 "수집 대상 서버군", "가상 네트워크", "단일 Engine VM", 3개 구간으로 구성했습니다. Monitoring Agent가 현재 환경 정보를 수집 서버까지 전달하는 조건을 재현하기 위한 환경입니다.

가용 자원으로는 사측이 이미 운영하던 "OpenStack 프라이빗 클라우드"를 활용했습니다. OpenStack은 여러 베어메탈 서버의 컴퓨팅, 네트워크와 스토리지 자원을 하나의 풀로 묶고, 그 위에 VM과 가상 네트워크를 반복해서 구성해야 할 때 적합합니다.

OpenStack은 검증 환경의 모든 VM과 네트워크를 관리합니다. Horizon과 API client가 관리 인터페이스이고, Nova와 Neutron이 컴퓨팅 및 네트워크 자원을 제어합니다.

"수집 대상 서버군"은 Linux 58대와 Windows 11대, 총 69대의 Agent VM입니다. 모든 VM에 C 기반 네이티브 Agent 바이너리를 설치했습니다. Linux는 6개 서브넷, Windows는 1개 전용 서브넷을 사용합니다. 각 Agent가 발행한 AMQP 메시지는 OpenStack Neutron의 assessment-router를 거쳐 단일 Engine VM으로 전달됩니다.

현장 수집 장비 역할의 "단일 Engine VM"에는 Docker Compose로 Web, Consumer, Worker, RabbitMQ, Redis, TimescaleDB를 함께 구성했습니다. 검증한 핵심 저장 경로는 "RabbitMQ -> Consumer -> TimescaleDB"입니다.

## 12. 검증 환경 접근 경로

접근 환경은 "최초 1회 구성"과 "반복 원격 작업", 2단계로 나뉩니다.

제공된 조건은 기업 연계 클라우드 인프라의 Windows jump host에 RDP(Remote Desktop Protocol)로 접속하고, 그 안에서 Horizon을 사용할 수 있는 권한이었습니다. "최초 1회 구성"에서는 Horizon으로 Linux control VM을 생성하고, 이 VM에 VPN(Virtual Private Network) SSH 접속과 서브넷 라우팅을 설정했습니다.

"반복 원격 작업"은 외부 작업 단말에서 2개 경로로 진행했습니다. 개발 경로는 VPN과 SSH를 통해 Linux control VM에 접속하고, VS Code Remote와 OpenStack API로 여러 VM을 자동 생성하고 관리합니다.

Horizon 접근 경로에서는 브라우저를 외부 작업 단말에서 실행합니다. Linux control VM이 VPN의 subnet router로 동작하므로, 로컬 브라우저에서 내부망 전용 주소를 가진 Horizon에 접근할 수 있습니다. OpenStack API와 Horizon은 모두 여러 Agent VM과 단일 Engine VM으로 구성된 같은 환경을 제어합니다.

## 13. OpenStack Horizon과 검증 서버군

"OpenStack Horizon"은 프라이빗 클라우드의 VM을 조회하고 생성하며 상태를 관리하는 웹 인터페이스입니다.

"혼합 OS 서버군" 목록에는 Linux, Windows, Engine VM이 함께 구성되어 있습니다. "Windows coverage" 목록에는 Windows Server 2003부터 최신 버전까지 세대별 검증 대상이 포함되어 있습니다.

## 14. Agent-Engine 배포 및 수집 경로 검증

검증 범위는 "Agent 배포"와 "Engine 구성", 2개 영역입니다. 수집 처리 경로는 4단계이고, 마지막으로 저장 결과를 확인했습니다.

Agent는 인터넷 연결을 전제하지 않고 3개 경로로 배포했습니다. "SSH"는 개별 서버에 직접 배포하고, "Ansible"은 같은 절차를 여러 서버로 확장합니다. "Offline injection"은 SSH 접근이 어려운 VM의 볼륨에 Agent 파일과 설정을 주입합니다. 이 방법들을 운영체제와 접근 조건에 맞게 적용해 Linux와 Windows에서 Agent 서비스를 기동했습니다.

Engine은 단일 VM에서 "Docker Compose"로 Web, Consumer, Worker와 데이터 서비스를 기동했습니다.

수집 및 확인 흐름은 "Agent 서비스 -> RabbitMQ -> Consumer -> TimescaleDB -> 저장 결과 확인"입니다. Agent 서비스가 인벤토리와 측정값을 발행하고, RabbitMQ가 메시지를 전달합니다. Consumer가 스키마를 검증해 TimescaleDB에 서버 정보와 시계열을 저장한 뒤, Engine에서 서버와 측정값이 조회되는지 확인했습니다.

## 15. 검증 환경 재현

검증 환경 재현은 Agent나 Engine을 수정한 뒤에도 같은 운영체제 조합과 네트워크 조건에서 다시 확인하기 위한 절차입니다. 환경이 매번 달라지면 결과 차이가 코드 변경 때문인지 환경 차이 때문인지 구분하기 어렵습니다.

인프라는 "Terraform -> OpenStack API -> 검증 환경" 순서로 구성합니다. Terraform으로 Agent VM, 네트워크, 단일 Engine VM을 선언하고, OpenStack API로 선언한 자원을 생성합니다.

검증 환경을 재현하는 과정에서 Agent를 초기 주입하는 방식은 2가지입니다. "Modern Linux"에서는 cloud-init으로 VM 생성 시 Agent와 설정을 자동 준비합니다.

"Legacy Linux / Windows"에서는 cloud-init을 같은 방식으로 전제할 수 없습니다. Agent VM의 부팅 볼륨을 임시 복구 VM에 연결해 파일과 설정을 주입하고, Windows에서는 registry hive까지 수정하는 Offline injection을 사용합니다.

## 16. Agent와 Engine

검증 환경을 구성하고 Agent를 배포해, 현재 환경 정보가 수집 서버의 데이터베이스까지 저장되는 흐름을 확인했습니다.

이 흐름의 핵심은 "Native Agent", "메시지 계약", "컴포넌트 구조", "비동기 처리"입니다. Agent는 운영체제별 정보를 공통 메시지로 만들고, Engine은 수집, 저장, 평가와 결과 전달을 나누어 처리합니다.

## 17. Agent 동작

Agent 동작은 "OS 정보 수집 -> raw 관측값 정규화 -> RabbitMQ 발행"의 3단계입니다. 발행 데이터는 "Inventory", "Metrics", "Envelope"의 3개 영역으로 구성됩니다.

Linux에서는 `/proc`, `/sys`, `/etc`의 커널 가상 파일과 시스템 파일을 읽어 CPU, 메모리, 디스크, 네트워크 측정값을 수집합니다. 서비스 목록과 일부 식별 정보는 systemd 또는 SysV 서비스 관리자와 클라우드 메타데이터 조회로 보완합니다. Windows에서는 registry, Windows API, I/O 제어 API(IOCTL)와 성능 계측값을 사용합니다.

Linux Agent는 "musl 정적 링크 바이너리"로 빌드합니다. Windows Agent는 구세대 호환을 위해 "i686 단일 바이너리"로 빌드하고, 실행 중인 Windows 세대에 맞게 동작을 나눕니다.

두 운영체제의 수집 결과는 Engine과 정한 공통 스키마와 단위로 정규화합니다. "Inventory"에는 운영체제, CPU, 스토리지, 네트워크, 서비스 구성을 넣습니다. "Metrics"에는 CPU, 메모리, 디스크, 네트워크의 가공하지 않은 누적값과 현재값을 넣습니다. "Envelope"에는 agent_id, collected_at, schema_version을 넣어 메시지의 발행 주체, 수집 시각과 계약 버전을 식별합니다.

Agent는 시간에 따른 변화량, 자원 사용률과 자원 적정성 판단을 계산하지 않습니다. "raw 관측값"만 RabbitMQ에 발행하고, 여러 시점의 값을 비교하는 계산과 평가는 Engine이 담당합니다.

## 18. Engine 컴포넌트 구조

시스템 경계를 기준으로 전체 구성요소는 8개입니다. Engine 밖에는 "Monitoring Agent"와 "사용자 및 연계 도구"가 있고, Engine 안에는 RabbitMQ, Consumer, TimescaleDB, FastAPI, Worker, Redis의 6개 구성요소가 있습니다.

수집과 저장은 "RabbitMQ -> Consumer -> TimescaleDB"가 담당합니다. RabbitMQ는 메시지를 전달하고, Consumer는 수신 데이터의 스키마를 검증해 저장하며, TimescaleDB는 인벤토리와 시계열을 보존합니다. "FastAPI"는 평가 결과를 화면과 API로 제공합니다. "Worker"는 보고서 생성과 설치 작업의 시간 초과 처리를 담당하고, "Redis"는 캐시, 온라인 상태와 중복 처리의 1차 차단을 맡습니다.

## 19. 수집 메시지 처리 시퀀스

수집 메시지 처리에는 Monitoring Agent, RabbitMQ, Consumer, Redis, TimescaleDB의 5개 구성요소가 참여하고, 정상 경로는 6단계입니다.

Monitoring Agent가 인벤토리 또는 raw 측정값을 "RabbitMQ"에 발행하면, RabbitMQ가 메시지를 "Consumer"에 전달합니다. Consumer는 먼저 스키마를 검증합니다.

이어 "SET NX"를 사용해 같은 message_id를 이미 처리했는지 Redis에서 1차로 확인합니다. NX는 Not eXists의 약자로, 키가 없을 때만 값을 저장하는 옵션입니다. Redis가 중단돼도 수집은 멈추지 않고, 데이터베이스의 UNIQUE 제약이 2차로 중복 저장을 막습니다.

정상 메시지는 메시지 1건 단위의 데이터베이스 트랜잭션으로 서버 정보를 갱신하거나 시계열을 저장합니다. "DB commit 후 ACK" 원칙에 따라 저장이 끝난 뒤 Consumer가 RabbitMQ에 ACK(Acknowledgement)를 보내면 처리가 완료됩니다.

형식이 잘못됐거나 재시도 한도를 넘긴 메시지는 "DLQ(Dead Letter Queue)"로 분리합니다.

## 20. Engine 아키텍처의 특징

Engine 아키텍처에는 "메시지 기반 수집", "DB 기반 백그라운드 작업", "영속 데이터와 보조 상태 분리"라는 3가지 특징이 있습니다.

첫째, Agent가 수집 서버 API를 직접 호출하면 Agent 발행, 서버 로직 처리와 데이터베이스 저장 속도가 하나의 요청에 묶입니다. 이 시스템은 "메시지 브로커로 수집 경로를 분리"했습니다. RabbitMQ의 내구성 큐가 Agent 발행과 Consumer 저장을 분리하고, Consumer 재시작이나 처리 속도 차이를 흡수합니다.

둘째, "HTTP 요청과 백그라운드 작업을 분리"했습니다. FastAPI는 오래 걸리는 작업을 데이터베이스에 등록하고 바로 응답합니다. Worker는 보고서 생성과 설치 작업의 시간 초과 처리를 별도 프로세스에서 담당하므로 HTTP(Hypertext Transfer Protocol) 요청과 작업 실행 시간이 분리됩니다.

셋째, "영속 데이터와 보조 상태를 분리"했습니다. TimescaleDB는 인벤토리, 시계열, 설치 작업과 보고서를 보존합니다. Redis는 캐시, 온라인 상태와 중복 처리의 1차 차단을 담당합니다. Redis에 장애가 나도 데이터베이스 조회와 UNIQUE 제약으로 핵심 처리를 계속합니다.

## 21. 핵심 기능 구현

Engine의 핵심 기능 구현은 "환경 및 서버 현황", "자원 적정성 평가", "보고서 발행", "ZDM 설치"의 4가지입니다. 수집한 현재 환경 정보를 조회하고 평가한 뒤, 결과를 공유하거나 자사 솔루션 적용으로 연결합니다.

## 22. 환경과 서버 현황 조회

Agent가 수집한 인벤토리와 측정값은 "환경 전체"와 "개별 서버", 2개 범위로 제공합니다. 환경 전체에서는 서버와 자원 합계, 운영체제와 워크로드 분포, 실시간 및 기간별 자원 상태를 집계해 보여 줍니다.

환경 집계에서 조사할 대상을 선별하면 "개별 서버"의 시스템 식별 정보, 스토리지와 네트워크, 서비스와 포트, 실시간 및 기간별 측정값을 확인할 수 있습니다. 별도 데이터를 만드는 것이 아니라, 같은 수집 정보를 "환경 집계 -> 대상 선별 -> 서버 상세" 순서로 범위에 맞게 제공합니다.

## 23. 자원 적정성 평가

자원 적정성 평가는 "현재 사양이 실제 사용량에 맞는가"라는 질문에서 시작합니다.

평가 범위는 서버마다 "CPU, 메모리, 디스크 용량, 디스크 I/O, 네트워크"의 5개 자원입니다. 각 자원에는 USE Method의 3가지 기준을 적용합니다. USE는 Utilization, Saturation, Errors의 첫 글자를 딴 방법입니다. "이용률"은 얼마나 사용했는지, "포화"는 대기나 병목이 있는지, "오류 신호"는 오류나 고장 징후가 있는지를 묻습니다. 5개 자원에 3가지 기준을 적용하므로 총 15개 평가 항목이 됩니다.

자원별 평가 결과는 이해하기 쉽게 3가지로 묶었습니다. "사양 권고"는 CPU, 메모리와 디스크 용량을 늘리거나 줄일지 판단합니다. "성능 상태"는 디스크 I/O와 네트워크의 병목을 보여 줍니다. "오류 진단"은 자원에서 발생한 오류 신호를 보여 줍니다.

처방은 자원별 결과를 서버 단위로 종합해 "부족, 과다 할당, 유휴, 적정, 표본 부족"으로 판정하고, 증설, 축소, 종료 및 통합, 유지 또는 관찰이라는 조치를 제시합니다.

안정장치는 3가지입니다. "기간으로 판단"하기 위해 기본 14일의 p95와 추세를 사용합니다. p95는 관측값의 95%가 이 값 이하에 놓이는 기간 대표값입니다. "OS 차이를 해석"해 Linux와 Windows의 서로 다른 측정값을 같은 3가지 질문으로 변환합니다. "확실할 때만 감축"하기 위해 노이즈와 미측정값은 관찰로 남기고, 이력과 추세가 충분할 때만 구체적인 감축 사양을 권고합니다.

## 24. 환경 자원 평가 화면

"환경 자원 평가"의 검증 환경은 69대로 구성했습니다. 촬영 당시에는 별도 테스트 VM 1대가 추가되어 화면에 70개 서버가 표시됩니다. 평가 기간과 기준 시각을 선택하고 3가지 결과를 확인합니다.

"환경 전체 분포"는 자원 부족, 과다 할당, 유휴, 적정, 표본 부족의 수를 보여 줍니다. "서버별 분류와 권고"는 현재 사양, 분류와 조치를 보여 줍니다. "성능 상태와 신뢰도"는 네트워크와 디스크 I/O 상태, 판정 신뢰도를 함께 보여 줍니다.


## 25. 보고서 스냅샷 생성

보고서 생성 구조는 "비동기 처리", "DB 작업 상태", "정적 스냅샷"의 3가지 특성을 결합합니다. 비동기 처리는 환경 전체나 여러 서버를 집계하는 동안 HTTP 연결을 계속 유지하지 않도록 요청과 생성을 분리합니다. DB 작업 상태는 생성 진행과 실패를 기록하고 조회하게 합니다. 정적 스냅샷은 이미 공유한 결과가 이후 수집 데이터 때문에 바뀌지 않게 합니다.

구현 흐름은 "발행 요청 -> pending 등록 -> 보고서 생성 -> 완료 결과 조회"의 4단계입니다. FastAPI는 범위, 기준 시각과 보고서 유형을 검증하고 pending 작업을 TimescaleDB에 등록한 뒤 식별자를 바로 반환합니다. Worker는 대기 중인 작업을 running으로 바꾸고 평가 결과와 보고서 JSON을 생성합니다. 생성 결과에 따라 succeeded 또는 failed로 바꾸고, 실패 원인을 저장합니다. 브라우저는 같은 작업의 상태를 주기적으로 확인하다 완료된 결과를 보여 줍니다.

동시에 들어온 동일 보고서 요청은 진행 중인 작업을 재사용합니다. 범위, 입력 조건과 보고서 유형이 같은 pending 또는 running 작업이 있으면 새 작업을 만들지 않고 기존 작업 식별자를 반환합니다. "정적 결과 보존"은 성공한 작업의 결과 JSON을 다시 계산하지 않고, 같은 URL에서 발행 시점의 값을 유지합니다.

## 26. 보고서 유형과 용도

보고서는 범위 2개와 독자 2개를 조합한 4가지 형태입니다. 범위는 "환경 보고서"와 "개별 보고서"이고, 독자는 "고객용"과 "엔지니어용"입니다.

"고객용 환경 보고서"는 환경 현황, 분류 분포와 조치 대상을 회의와 보고에 맞게 요약합니다. "엔지니어용 환경 보고서"는 같은 환경 요약과 평가 결론에 부하 추이, 네트워크 토폴로지와 서버별 판정 근거를 더합니다.

"고객용 개별 보고서"는 선택한 서버의 구성, 주요 지표와 평가 결론을 간결하게 전달합니다. "엔지니어용 개별 보고서"는 고객용 내용에 자원별 통계, 포화와 오류 신호, 신뢰도와 시스템 상세를 더합니다.

4개 보고서는 서로 다른 평가를 수행하지 않습니다. 같은 범위와 기준 시각의 수집 정보와 평가 결과를 독자에 맞게 구성하며, 엔지니어용은 고객용 정보를 모두 포함하고 상세 근거를 추가합니다.

## 27. ZDM 설치 작업과 결과 회신

ZDM은 자사가 제공하는 솔루션을 서버에 적용할 때 사용하는 매개체입니다. 설치 작업은 "작업 발행 -> 서버별 전달 -> 검증 및 설치 -> 결과 저장"의 4단계입니다.

운영자는 서버 목록에서 대상을 선택하고 "Install" 버튼으로 작업을 발행합니다. Engine은 대상 서버, ZDM 주소와 계정을 검증해 pending 작업을 저장합니다. RabbitMQ는 agent_id가 포함된 routing key로 지정 Agent의 큐에 작업을 전달합니다.

Agent는 허용된 다운로드 호스트, 파일 크기와 checksum을 확인한 뒤 운영체제에 맞는 ZDM 패키지를 실행합니다. 실행 결과는 task.result 메시지로 Engine에 돌아오고, Consumer는 성공 또는 실패 상태, 종료 정보와 로그 마지막 부분을 저장합니다.

## 28. ZDM 설치 상태 확인

설치 결과는 "서버별 상태"와 "작업 결과 모달", 2개 수준으로 확인합니다. 작업 상태는 "진행 중, 성공, 실패"의 3가지입니다.

서버 목록의 ZDM Install 배지는 작업을 발행한 직후 진행 중으로 표시되고, Agent 결과가 도착하면 성공 또는 실패로 갱신됩니다. 기한 안에 결과가 없으면 실패 상태와 시간 초과 사유가 남습니다.

배지를 선택하면 "작업 결과 모달"에서 발행과 완료 시각, 소요 시간, 종료 정보와 실패 사유를 확인할 수 있습니다. 상세 로그가 필요하면 표준 출력과 표준 오류의 마지막 부분에서 설치 실패 원인을 확인합니다.

## 29. 유즈케이스와 결과

현재 환경 정보와 평가 결과가 활용되는 대표적인 유즈케이스 2개를 살펴보고, 마지막으로 프로젝트의 결과를 종합하겠습니다.

## 30. 환경 진단과 조치 우선순위

첫 번째 사용 사례는 "환경 진단과 조치 우선순위"입니다. 업무 흐름은 "분포 확인 -> 대상 선별 -> 상세 확인 -> 조치 결정"의 4단계입니다.

"분포 확인"에서는 과다 할당, 유휴, 자원 부족과 적정 상태의 규모를 파악합니다. 수십 대의 서버 상세 정보를 처음부터 하나씩 확인하지 않아도 됩니다.

"대상 선별"에서는 서버별 CPU, 메모리, 디스크 사양과 분류, 권고, 네트워크와 디스크 I/O 상태, 신뢰도를 비교해 조치 후보와 확인 순서를 정합니다.

"상세 확인"에서는 선택한 서버의 CPU, 메모리와 스토리지 중 어떤 자원이 판정의 원인인지 확인합니다. "조치 결정"에서는 자원이 부족하면 증설하고, 과다 할당이면 축소 가능성을 검토합니다. 장기간 활동이 거의 없으면 통합 후보로 검토하고, 관측이 충분하지 않으면 변경하지 않고 관찰을 이어 갑니다.

이 흐름은 서버 운영 업무에서 조치 후보를 찾고, 서버별 근거를 바탕으로 확인 및 처리 순서를 정하는 데 사용합니다.

## 31. 클라우드 이전 및 재해복구 설계

두 번째 사용 사례는 "클라우드 이전 및 재해복구 설계"입니다. 흐름은 "현재 서버 정보 -> Assessment API 또는 JSON Export -> VM 사양과 구성안"의 3단계입니다.

"현재 서버 정보"에는 운영체제와 부팅 정보, CPU와 메모리, 스토리지, 네트워크와 서비스가 있습니다. 여기에 실사용량과 규칙 기반 분류를 결합해 단순 복제가 아니라 현재 부하를 고려한 설계 근거를 만듭니다.

"Assessment API"는 이 정보를 API 호출로 제공하고, "JSON Export"는 같은 정보를 파일로 제공합니다. Terraform 같은 IaC(Infrastructure as Code) 도구와 클라우드 이전 도구가 같은 결과를 입력으로 사용할 수 있습니다.

ZConverter Assessment 시스템의 책임은 새 환경 설계에 필요한 근거를 제공하는 데까지입니다. 이 근거를 바탕으로 VM을 생성하고 실제 클라우드 이전을 수행하는 일은 외부 도구가 담당합니다.

## 32. ZConverter Assessment 시스템이 만드는 결과

앞서 프로젝트의 목표를 "현재 환경 정보를 원하는 범위와 수신자에 맞는 평가 결과로 제공하는 것"으로 정했고, 이를 "ZConverter Assessment"라는 제품으로 구체화했습니다.

출발점은 클라우드 이전과 재해복구에 필요한 설계 근거였습니다. ZConverter Assessment는 같은 수집 정보와 평가 결과를 Dashboard, Report, Assessment API와 JSON Export로 제공합니다. 이 특징을 통해 서버 운영과 자동화 도구까지 활용 범위를 넓혔습니다.

서버 운영 담당자는 Dashboard와 Report에서 조치 후보와 우선순위를 확인합니다. 마이그레이션 설계자는 현재 사양과 평가 결과를 VM 사양과 재해복구 구성안을 검토하는 근거로 사용합니다. Terraform 같은 자동화 도구는 Assessment API와 JSON Export로 제공되는 데이터를 입력으로 활용할 수 있습니다.

클라우드 이전과 재해복구를 위한 환경 파악에서 시작해, 같은 정보를 운영 판단과 자동화에도 활용할 수 있게 만든 것이 이 프로젝트의 결과입니다. 감사합니다.
