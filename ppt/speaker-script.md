# ZConverter Assessment 발표 대본

## 1. ZConverter Assessment

안녕하세요. 저희 2팀은 고객 내부망 서버의 현재 상태를 지속해서 수집하고, 공통 규칙으로 자원 적정성을 평가하는 ZConverter Assessment를 구축했습니다.

오늘은 기술 구성 자체보다 왜 이 시스템이 필요한지, 사용자가 어떤 업무를 끝낼 수 있는지, 실제 혼합 OS 환경에서 어디까지 확인했는지를 중심으로 말씀드리겠습니다.

## 2. 배경과 프로젝트 정의

먼저 현재 환경 정보가 왜 필요한지부터 프로젝트의 목표와 제품의 역할까지 설명하겠습니다.

## 3. 기업 연계 과제의 출발점

클라우드 이전이나 재해복구 환경을 준비하려면 원천 서버와 비슷한 대상 VM 사양을 먼저 정해야 합니다. 이때 필요한 것은 서버 이름과 명목 사양만이 아닙니다. 어떤 OS를 쓰는지, CPU와 메모리가 얼마나 할당돼 있는지, 스토리지가 어떻게 구성돼 있는지, 실제로는 어느 정도 사용하는지를 함께 알아야 합니다.

고객 내부망에는 서로 다른 세대와 운영체제의 서버가 섞여 있습니다. 서버별 자원 구성과 실제 사용량을 함께 알지 못하면, 클라우드 대상 VM 사양도 추측에 의존하게 됩니다.

이 프로젝트는 서버 정보와 실사용량을 함께 파악해 클라우드 이전과 재해복구 사양의 근거를 만드는 일에서 출발합니다.

## 4. 의사결정 정보의 공백

클라우드 이전과 재해복구 대상 VM 사양을 정하려면 먼저 3가지 정보를 파악해야 합니다.

현재 고객사는 고객 내부망 서버의 사양을 Excel로 작성해 관리하고 있습니다. 이 방식은 기본 구성 확인에는 쓸 수 있지만, 실제 사용량과 시간에 따른 변화 추세를 파악하기는 어렵습니다.

첫째는 자원 구성입니다. OS, CPU, 메모리, 스토리지, 네트워크가 현재 어떻게 구성됐는지를 알아야 합니다. 둘째는 실제 사용량입니다. 평균 사용량뿐 아니라 피크 사용량과 자원별 병목도 함께 봐야 합니다. 셋째는 변화 추세입니다. 용량이 얼마나 빨리 소진되는지, 사용량이 상승하는지, 포화가 반복되는지를 관측해야 합니다.

이 정보가 없으면 대상 VM 사양 판단은 2가지 방향으로 왜곡됩니다. 사양을 너무 작게 잡으면 클라우드 이전이나 재해복구 이후 성능 저하와 중단 위험이 생깁니다. 반대로 너무 크게 잡으면 사용하지 않는 자원에 비용을 계속 지불합니다.

이 3가지 정보를 지속해서 확보해 필요한 범위와 수신자에게 전달하는 것이 프로젝트의 목표입니다.

## 5. 프로젝트의 목표

프로젝트의 목표는 현재 환경의 사실을 필요한 사람이 사용할 수 있는 평가 결과로 제공하는 것입니다. 자원 구성, 실제 사용량, 변화 추세를 함께 정리합니다.

제공 범위는 환경 전체, 선택한 서버 묶음, 개별 서버입니다. 고객에게는 결론과 조치 중심의 결과를, 엔지니어에게는 근거와 세부 진단을 전달합니다.

다음 페이지에서는 모니터링 Agent, 수집 백엔드 서버, 결과 전달 수단이 이 목표를 3단계로 구현하는 방식을 보겠습니다.

## 6. ZConverter Assessment

제품의 핵심 흐름은 3단계입니다.

첫째, 모니터링 Agent가 고객 내부망 서버의 인벤토리와 메트릭을 수집 백엔드 서버로 전달합니다.

둘째, 수집 백엔드 서버는 전달받은 데이터를 같은 규칙으로 분류하고 자원 적정성과 운영 신호를 평가합니다.

셋째, 결과를 전달합니다. Web Dashboard는 현재 상태와 상세 정보를 탐색하는 화면이고, Report는 고객에게는 결론과 조치를, 엔지니어에게는 근거와 세부 진단을 제공합니다. Assessment API와 JSON Export는 자동화 도구의 입력입니다.

같은 수집 데이터와 같은 규칙을 모든 전달 수단이 공유하므로, 화면, 보고서, 자동화 도구 사이에서 판단 기준이 달라지지 않습니다. 다음 페이지에서 이 역할을 실제 제품 구성으로 보겠습니다.

## 7. Assessment 아키텍처

그림에는 3개 배치 영역이 있습니다. 가장 바깥 점선은 고객 내부망입니다. 왼쪽은 실제 업무 서버들로 이루어진 Agent fleet이고, 오른쪽은 이 환경 안에서 동작하는 Engine host입니다. Engine host 안의 실선이 Assessment Engine의 경계입니다.

각 업무 서버에는 Monitoring Agent가 설치됩니다. Server A, B, N의 Agent 모두가 인벤토리와 메트릭을 AMQP 메시지로 RabbitMQ에 발행합니다. 이 화살표가 수집 대상 서버와 수집 백엔드 사이의 실제 실행 흐름입니다.

Engine host의 위쪽 배치는 수집 경로입니다. RabbitMQ가 메시지를 전달하고, Consumer가 검증과 저장을 담당하며, TimescaleDB가 시계열 데이터를 저장합니다. 아래쪽에는 TimescaleDB의 정보를 Web과 REST API로 제공하는 FastAPI, 보고서와 시간 초과 처리를 맡는 Worker, cache와 온라인 상태 같은 보조 상태를 맡는 Redis를 배치했습니다.

핵심 실행 흐름은 Agent fleet에서 RabbitMQ로, 이어서 Consumer와 TimescaleDB로 흐릅니다. 조회 흐름은 TimescaleDB에서 FastAPI를 거쳐 Web과 REST API로 이어집니다.

## 8. Assessment 기능

Assessment 기능은 주 기능 3개와 파생 기능 4개로 나눕니다.

주 기능은 자원 적정성 평가로 이어지는 흐름입니다. Monitoring Agent가 현재 환경 정보를 수집하고, 시계열로 저장해 피크와 변화 추세를 누적합니다. 그 위에서 공통 규칙으로 자원 적정성, 운영 신호, 권고를 평가합니다.

파생 기능은 평가 결과를 사용하는 방식입니다. Web Dashboard에서 현황을 탐색하고 서비스를 분류하며, Customer와 Engineer Report로 결과를 공유합니다. Assessment API와 JSON Export는 외부 도구와 연계하며, ZDM 설치 작업은 전환 작업의 실행 결과를 추적합니다.

이제 이 기능들이 동작할 현장 조건과 검증 환경을 보겠습니다.

## 9. 현장 조건과 검증

이제 현장에서 마주칠 조건을 어떻게 시험 환경으로 옮겼고, 실제 수집 경로를 어디까지 확인했는지 보겠습니다.

## 10. 현장 조건

이 페이지는 고객 환경을 이미 안다고 두는 상정 환경이 아닙니다. 현장에 수집 장비를 반입하기 전에 확인해야 하는 조건입니다.

확정된 요구는 2개입니다. OS coverage는 CentOS와 RHEL 6부터 현대 Linux, Windows Server 2003 SP1부터 현대 버전까지입니다. Native Agent는 OS별 C 기반 단일 binary를 각 서버에서 실행한다는 요구입니다.

현장에서 확인할 사항은 2개입니다. 내부망 플랫폼은 물리 환경인지, public cloud인지, OpenStack 같은 private cloud인지 사전에 확정할 수 없습니다. 인터넷 연결과 SSH 접근 가능 여부도 현장마다 다릅니다. GitHub에서 Agent를 직접 내려받는 방식은 배제했습니다.

이 조건에서 배포 경로를 도출했습니다. 검증에서는 SSH 직접 배포, 같은 SSH 절차를 확장하는 Ansible, SSH 접근이 어려운 상황을 위한 offline injection을 사용했습니다. USB로 직접 주입하는 방식은 별도로 검증하지 않았습니다.

다음 페이지는 이 현장 조건에 대응하기 위해, 우리가 가용한 OpenStack 자원으로 구성한 시험 환경입니다.

## 11. 검증 환경 구성

현장 조건이 있었고, 그에 대응할 가용 자원으로 OpenStack private cloud를 활용했습니다. OpenStack은 가상 컴퓨팅, 네트워크, 스토리지 자원을 제공하는 private cloud 플랫폼입니다.

그림의 아래 막대가 OpenStack 관리 계층입니다. Agent fleet, assessment-router, 단일 Engine VM은 모두 OpenStack 위에 있습니다. Horizon dashboard 또는 API client로 Nova와 Neutron control plane을 조작하고, Compute hypervisor와 virtual network가 VM과 네트워크를 제공합니다. Linux 58대와 Windows 11대, 합계 69대의 각 VM에는 C 기반 Native Agent binary를 설치했습니다. Linux는 6개 subnet, Windows는 전용 subnet을 사용하고 assessment-router를 거쳐 단일 Engine VM의 container stack으로 메시지를 전달합니다. 이 VM은 현장 수집 장비가 수행할 수집과 평가 역할을 검증 환경에서 재현합니다.

Agent 배포는 SSH 직접 배포, Ansible 확장, offline injection으로 검증했습니다. 수집 장비 역할의 Engine stack은 반입과 기동이 가장 간단한 Docker Compose로 Web, Consumer, Worker와 RabbitMQ, Redis, TimescaleDB를 함께 구성했습니다.

이 환경은 Monitoring Agent가 서버 fleet에서 Engine까지 현재 환경 정보를 전달하는 경로를 확인하기 위한 공통 무대입니다.

## 12. 검증 환경 접근 경로

주어진 조건은 Horizon에 접근할 수 있는 Windows jump host의 RDP 접근 권한이었습니다. 이 경로가 검증 환경을 처음 관리할 수 있는 출발점이었습니다.

제공된 Horizon browser에서 Linux control VM을 1회 생성했습니다. 이 VM은 이후 VPN SSH와 subnet routing의 제어 지점입니다.

반복되는 원격 접근 흐름은 이 Linux control VM을 중심으로 동작합니다. SSH로 VS Code Remote를 사용해 OpenStack API를 호출하면 여러 VM을 자동으로 생성하고 관리할 수 있습니다. subnet routing은 같은 Linux control VM을 경유해 원격 작업 환경 브라우저의 Horizon 접근을 제공합니다. Horizon은 같은 VM fleet을 화면으로 제어하는 경로입니다. 이 VM fleet에는 여러 Agent VM과 단일 Engine VM이 함께 있습니다.

## 13. OpenStack Horizon과 검증 fleet

구성도는 설계한 검증 환경이고, 이 화면은 OpenStack Horizon에서 실제로 확인한 인스턴스 목록입니다.

왼쪽은 Linux, Windows, Engine VM이 함께 있는 혼합 OS fleet입니다. 오른쪽은 Windows Server 2003부터 현대 버전까지의 세대별 검증 대상입니다. 이 화면으로 OS coverage가 문서상의 가정이 아니라 실제 Horizon 인스턴스 목록에서 구성한 범위임을 확인했습니다.

## 14. 검증 환경 재현

앞의 화면은 실제로 구성한 검증 환경이고, 이 페이지는 그 환경을 다시 만들기 위해 사용한 수단입니다.

주 흐름은 Terraform이 Agent fleet VM, 네트워크, 단일 Engine VM을 선언하고 OpenStack API가 이를 생성하는 구조입니다. 따라서 같은 검증 구성을 반복해 준비할 수 있습니다.

Agent 설치와 초기 준비에는 2가지 선택지가 있습니다. cloud-init은 Linux Agent fleet 준비를 자동화합니다. offline injection은 rescue volume attach와 Windows registry hive를 포함하는 Agent 주입 방식입니다. 대상 조건에 맞는 하나의 경로를 사용합니다.

## 15. Agent-Engine 배포 및 수집 경로 검증

검증에서는 Agent와 Engine을 각각 준비한 뒤, 두 배포 결과가 하나의 수집 경로로 연결되는지 확인했습니다.

Agent는 SSH 직접 배포, Ansible 확장, offline injection 경로를 사용해 Linux와 Windows에서 서비스를 기동했습니다. Engine은 단일 VM에서 Docker Compose로 Web, Consumer, Worker와 RabbitMQ, Redis, TimescaleDB를 기동했습니다.

Agent service가 inventory와 metrics를 RabbitMQ에 발행하고, Consumer가 메시지를 검증해 TimescaleDB에 서버 inventory와 시계열을 저장하는 구간까지 확인했습니다. 이 결과는 배포와 수집 경로에 대한 검증이며, 자원 판정 정확도나 장기 운영 안정성, 고객 운영 배포 전체를 의미하지 않습니다.

## 16. Agent와 Engine

검증된 경로 안에서 Agent와 Engine이 각각 어떤 책임을 맡는지 살펴보겠습니다.

## 17. Agent 동작

Monitoring Agent는 Linux의 CPU, 메모리, 디스크, 네트워크 측정값을 `/proc`, `/sys`, `/etc`의 커널 가상 파일과 시스템 파일에서 직접 읽어 파싱합니다. 서비스 목록과 일부 식별 정보는 systemctl과 메타데이터 조회로 보완합니다. Windows에서는 registry, Windows API, IOCTL, 성능 계측값을 사용합니다.

Linux Agent는 musl 기반 정적 링크 binary이고, Windows Agent는 구세대 호환을 위해 단일 i686 binary로 빌드해 런타임 세대를 분기합니다.

두 OS의 수집 결과는 Engine과의 스키마 계약에 맞는 공통 메시지 구조와 단위로 정규화합니다. Agent는 OS와 하드웨어 구성, 스토리지, 네트워크, 서비스의 현재 구성을 inventory로 보내고, CPU, 메모리, 디스크, 네트워크 측정값은 raw counter와 gauge로 보냅니다. envelope에는 agent_id, 수집 시각, schema version을 함께 넣습니다.

Agent는 rate, utilization, 자원 적정성 판단을 계산하지 않습니다. raw 관측값만 RabbitMQ에 발행하고, 계산과 평가는 Engine이 담당합니다. Agent 배포와 Engine의 설치 작업은 뒤의 별도 페이지에서 설명합니다.

## 18. Engine 컴포넌트 구조

Agent와 Engine의 메시지 경계는 RabbitMQ입니다. Agent는 server 이벤트를 발행하고 task 메시지를 수신합니다. RabbitMQ는 Consumer에 수집 메시지를 전달하고, FastAPI가 만든 설치 task를 지정 Agent로 라우팅합니다.

Consumer는 메시지 schema 검증, 멱등성, DLQ 처리를 담당하고 TimescaleDB에 저장합니다. TimescaleDB는 inventory, raw metrics, task, report job의 source of truth입니다. FastAPI는 DB와 Redis를 읽어 평가와 결과 제공을 맡고, Worker는 DB의 보고서 job과 task timeout을 처리합니다. Redis는 cache, 온라인 TTL과 중복 처리의 1차 차단을 맡는 fail-open 보조 저장소입니다.

## 19. 수집 메시지 처리 시퀀스

이 페이지는 Agent가 보낸 수집 메시지 1건의 정상 처리 경로만 보여 줍니다. Agent는 inventory 또는 raw metrics 메시지를 RabbitMQ에 발행하고, RabbitMQ는 Consumer에 전달합니다.

Consumer는 먼저 envelope과 데이터 구조를 검증하고 중복 처리 여부를 확인합니다. 정상 메시지는 1 메시지 단위 DB 트랜잭션으로 inventory를 upsert하거나 시계열을 저장합니다. 저장이 끝난 뒤 Consumer가 RabbitMQ에 ACK를 보내면 메시지 처리가 완료됩니다.

형식이 잘못됐거나 재시도 한도를 넘긴 메시지는 DLQ로 분리합니다. FastAPI, Worker, 설치 작업과 보고서 생성은 이 시퀀스에 넣지 않았습니다. 각각 뒤의 보고서와 ZDM 설치 페이지에서 별도 흐름으로 설명합니다.

## 20. Engine 아키텍처의 특징

첫 번째 선택은 Broker를 이용한 수집 경로 분리입니다. Agent와 Consumer 사이의 RabbitMQ durable queue가 Consumer 재시작과 발행 및 DB 저장 속도의 차이를 흡수합니다.

두 번째 선택은 요청과 긴 작업의 실행 수명 분리입니다. FastAPI는 DB에 Job을 등록하고, Worker는 대기 중인 작업을 가져와 보고서 생성과 task timeout을 별도 프로세스에서 처리합니다. HTTP 요청이 긴 작업의 완료를 기다리지 않습니다.

세 번째 선택은 영속 데이터와 보조 상태의 분리입니다. TimescaleDB는 inventory, 시계열, task, report의 source of truth입니다. Redis는 cache, 온라인 TTL, 멱등성 1단과 신호 빈도 제어를 맡습니다. Redis 장애 시 DB 조회와 UNIQUE 제약으로 전환해 핵심 처리를 계속합니다.

## 21. 핵심 기능 구현

전체 구조에서 한 단계 더 들어가 환경과 서버 현황, 평가 규칙, 비동기 보고서, 제한된 설치 작업이라는 4가지 핵심 구현을 보겠습니다.

## 22. 환경과 서버 현황 조회

Agent가 수집한 인벤토리와 메트릭은 환경 전체와 개별 서버라는 2개 범위로 제공됩니다. 환경 개요에서는 등록 서버 수, vCPU, 메모리와 디스크 합계, OS 지원 상태, 주요 워크로드와 자원 상태를 집계해 보여 줍니다.

환경에서 확인할 대상을 고르면 개별 서버 상세로 내려갑니다. 서버 상세에서는 OS와 CPU 및 메모리, 스토리지와 네트워크 구성, 실행 중인 서비스와 포트, 실시간 자원 상태와 기간 추이를 함께 확인합니다. 별개의 데이터를 만드는 것이 아니라 같은 수집 결과를 조사 범위에 맞게 집계하거나 상세화하는 구조입니다.

## 23. 자원 적정성 평가

평가 단위는 5개 자원과 USE Method의 3개 축을 곱한 15개 관측 영역입니다. CPU, 메모리, 디스크 용량, 디스크 I/O, 네트워크마다 이용률, 포화, 오류 신호를 각각 확인합니다. 예를 들어 CPU는 사용률, 실행 큐, Machine Check를 보고 네트워크는 처리량, drop과 conntrack, 재전송과 NIC 오류를 봅니다. 디스크 I/O의 활동률은 단독 분류값이 아니라 await 판정에서 저활동 구간을 제외하는 보조 기준입니다.

15개 관측 영역은 같은 종류의 판정으로 합쳐지지 않습니다. CPU, 메모리, 디스크 용량은 사이징 판정으로 연결하고, 디스크 I/O와 네트워크는 성능 및 품질 상태로 표시합니다. 오류는 자원별 health 진단으로 별도 노출합니다. 사이징 판정을 서버 단위로 종합해 자원 부족, 과다 할당, 유휴, 적정, 표본 부족으로 분류하고 권고를 만듭니다.

평가는 기본 14일과 p95 같은 기간 대표값을 사용합니다. Linux와 Windows의 서로 다른 신호원은 공통 평가 축으로 해석하고, 이중 조건과 저활동 필터로 순간 노이즈를 제외합니다. 측정하지 못한 축은 값을 추정하지 않고 신뢰도 단서로 남깁니다. 감축은 이력과 관측 범위가 충분하고 이용률 추세가 안정적일 때만 구체적인 사양을 제시합니다.

## 24. 환경 자원 평가 화면

이 화면은 앞의 평가 규칙이 실제 웹페이지에서 어떻게 제공되는지를 보여 줍니다. 상단에서 평가 대상 70개 서버, 기본 14일 평가 기간, 기준 시각을 선택합니다.

먼저 환경 전체의 자원 적정성 분포로 자원 부족, 과다 할당, 유휴, 적정, 표본 부족의 개수를 확인합니다. 아래 표에서는 서버별 현재 사양, 분류, 권고, 네트워크 상태, 디스크 I/O 상태와 신뢰도를 함께 확인합니다.

앞 페이지의 관측 영역을 사이징 판정, 성능 및 품질 상태와 오류 진단으로 나눈 결과입니다.

## 25. 보고서 스냅샷 생성

보고서 생성 구조는 3가지 책임을 나눕니다. 비동기 처리는 환경 전체 또는 선택한 여러 서버를 집계하는 동안 HTTP 연결을 유지하지 않도록 요청과 생성을 분리합니다. DB job 상태는 생성 진행과 실패를 기록하고 조회하게 합니다. 정적 스냅샷은 이미 공유한 결과가 이후 데이터 수집으로 바뀌지 않게 고정합니다.

FastAPI는 범위, 기준 시각과 보고서 유형을 검증하고 pending job을 TimescaleDB에 등록한 뒤 job 식별자를 바로 반환합니다. Worker는 대기 중인 job을 가져와 running으로 전환하고, 공용 평가 ViewModel과 보고서 결과 JSON을 생성합니다. 생성이 끝나면 succeeded, 실패하면 failed 상태와 오류를 저장합니다. 브라우저는 같은 job을 polling하다 완료된 결과를 렌더링합니다.

같은 범위, 입력과 보고서 유형의 작업이 이미 진행 중이면 새 작업을 중복 생성하지 않고 기존 job에 합류합니다. succeeded job은 결과 JSON을 다시 계산하지 않으므로 같은 URL은 항상 발행 시점의 값을 보여 줍니다.

## 26. 보고서 유형과 용도

보고서는 범위 2개와 독자 2개를 조합한 4가지 형태입니다. 행은 환경 전체와 개별 서버이고, 열은 고객용과 엔지니어용입니다.

고객용 환경 보고서는 등록 서버, 자원 합계, 분류 분포와 조치 대상을 고객 회의와 내부 보고에 맞게 요약합니다. 엔지니어용 환경 보고서는 같은 환경 요약과 평가 결론을 바탕으로 상세 메트릭, OS와 서비스 구성, 부하 추이, 네트워크 토폴로지와 전체 서버의 판정 근거를 제공합니다.

고객용 개별 보고서는 선택한 서버의 인벤토리, 주요 지표와 평가 결론을 간결하게 전달합니다. 엔지니어용 개별 보고서는 같은 인벤토리와 평가 결론을 바탕으로 자원별 통계, 포화 및 오류 신호, 신뢰도, 시스템 식별자와 구성 상세, 재부팅 및 Agent 재시작 정보를 제공합니다.

4개 보고서는 서로 다른 평가를 수행하지 않습니다. 같은 범위와 기준 시각의 결과를 독자에 맞게 재구성하고, 엔지니어용은 같은 결론에 상세 근거를 더합니다.

## 27. ZDM 설치 작업과 결과 회신

운영자는 서버 목록에서 설치 대상을 체크하고 Install 버튼으로 작업을 발행합니다. Engine은 대상 서버, ZDM 주소와 계정을 검증해 pending task를 만들고, RabbitMQ는 서버의 agent ID가 포함된 routing key로 지정 Agent의 queue에 작업을 전달합니다.

Agent는 다운로드할 패키지를 검증하고 OS에 맞는 ZDM 설치를 실행합니다. 실행 결과는 task.result 메시지로 Engine에 돌아오고, Consumer는 성공 또는 실패 상태와 종료 정보 및 로그 tail을 저장합니다.

## 28. ZDM 설치 상태 확인

운영자는 서버 목록의 ZDM Install 배지에서 서버별 작업 상태를 바로 확인합니다. 발행 직후에는 진행 중으로 표시되고, Agent의 결과가 도착하면 성공 또는 실패로 자동 갱신됩니다. 기한 내 결과가 없으면 실패 상태와 timeout 사유가 남습니다.

배지를 선택하면 발행 및 완료 시각, 소요 시간, 종료 정보와 실패 사유를 확인할 수 있습니다. 상세 로그가 필요하면 stdout과 stderr tail로 설치 실패 원인을 추적합니다.

## 30. 환경 진단과 조치 우선순위

첫 번째 사용 사례는 환경 진단과 조치 우선순위 결정입니다.

운영 담당자는 수십 대의 서버 상세 화면을 처음부터 하나씩 열 필요가 없습니다. 환경 자원 평가 화면에서 자원 부족, 과다 할당, 유휴, 정상, 표본 부족의 분포를 먼저 확인합니다.

그다음 조치가 필요한 서버를 선별합니다. 서버별 표에는 현재 CPU, 메모리, 디스크 사양과 분류, 권고, 네트워크와 디스크 I/O 상태, 판단 신뢰도 단서가 함께 표시됩니다.

대상을 선택한 뒤 해당 서버의 상세 화면으로 내려가 어떤 자원이 원인인지 확인합니다. 자원이 부족하면 증설 방향을 보고, 과다 할당이면 축소 가능성을 검토하고, 장기간 활동이 거의 없으면 통합이나 종료 후보로 검토합니다. 관측이 충분하지 않으면 즉시 변경하지 않고 관찰을 이어 갑니다.

이 사용 사례의 결과는 단순한 상태 확인이 아니라 어떤 서버를 어떤 순서로 조치할지 정한 우선순위 목록입니다.

## 31. 클라우드 이전 및 재해복구 설계

두 번째 사용 사례는 클라우드 이전과 재해복구 대상 설계입니다.

대상 VM 사양 제시는 별도 판단이 아니라 개별 서버의 규칙 기반 분류를 활용하는 방식입니다. 원천 서버에는 OS와 부팅 정보, CPU와 메모리, 스토리지 계층, 네트워크와 서비스 정보가 있습니다. 여기에 관측 기간의 실사용량과 자원 평가 결과를 결합하면 단순 복제가 아니라 현재 부하를 고려한 대상 사양을 작성할 수 있습니다.

Assessment API는 이 정보를 HTTP로 제공합니다. JSON Export는 같은 계약을 파일로 전달합니다. 클라우드 이전 도구가 Engine에 직접 접속할 수 있으면 API를 사용하고, 직접 연결할 수 없거나 특정 시점의 원천 상태를 보관해야 하면 Export 파일을 사용합니다.

클라우드 이전 및 재해복구 솔루션은 이 결과를 설계 근거로 사용합니다. Engine의 책임은 대상 VM 사양과 구성안을 검토할 수 있는 근거를 제공하는 데까지입니다. 실제 VM 생성과 데이터 마이그레이션은 해당 솔루션이 담당합니다.

## 32. ZConverter Assessment 시스템이 만드는 결과

마지막은 ZConverter Assessment가 실제 업무에 제공하는 결과를 정리하는 페이지입니다.

운영 담당자는 Dashboard와 Report에서 조치 후보와 우선순위, 서버별 판단 근거를 확인합니다. 마이그레이션 설계자는 VM 사양과 재해복구 구성안의 판단 근거를 사용합니다. 자동화 도구는 Assessment API와 JSON Export를 입력으로 사용합니다.

즉 하나의 현재 환경 정보를 운영, 마이그레이션과 자동화 업무가 각자의 방식으로 재사용할 수 있게 만든 것이 프로젝트의 결과입니다. 감사합니다.
