# Alembic 정리 — 무엇을 푸는 도구이고 이 저장소에서 어떻게 쓰나

임시 자료 — 내부 학습용, 삭제 자유. Alembic 을 처음 다룰 때 필요한 개념과 명령, 그리고 이 저장소가 파일을 왜 그 위치에 뒀는지를 담는다.

## 1. 푸는 문제

코드의 ORM 모델은 git 이 이력을 관리한다. DB 스키마는 그렇지 않다. 개발 DB, 테스트 DB, 운영 DB 가 각자 다른 시점에 만들어져 서로 다른 모양일 수 있고, 어느 변경이 어디까지 적용됐는지 아무도 기억하지 못한다.

Alembic 은 스키마 변경 하나하나를 리비전 파일로 기록하고, 각 DB 가 자기가 어디까지 왔는지 스스로 알게 해서 누락분만 적용한다. 이력 기록과 적용 메커니즘이 한 몸이다 — 기록만 있으면 파일 더미고, 적용만 있으면 무엇을 적용할지 알 수 없다.

"모델을 보고 DB 를 알아서 맞춰준다"는 도구가 아니다. 사람이 리비전을 만들고 그 안에 올리는 방법(`upgrade`)과 되돌리는 방법(`downgrade`)을 명시한다. 자동 생성은 초안을 써줄 뿐이다.

## 2. 구성 요소 넷

| 요소 | 역할 |
|------|------|
| 설정 파일(`.ini`) | 리비전 디렉토리 위치와 DB 접속 방식을 지정 |
| `env.py` | 실행 진입점. DB 에 연결하고 어떤 모델을 기준으로 삼을지 정한다 |
| `versions/*.py` | 리비전 파일. 하나가 스키마 변경 하나 |
| `alembic_version` 테이블 | DB 안에 있다. 그 DB 가 현재 어느 리비전까지 왔는지 한 줄로 보관 |

마지막 것이 핵심이다. 환경마다 자기 상태를 DB 안에 들고 있어서, 같은 명령을 어디서 돌려도 그 환경에 필요한 만큼만 실행된다.

## 3. 리비전이 쌓이는 방식

각 리비전은 자기 id 와 부모 id 를 갖는다. 그래서 전체가 사슬이 된다. 이 저장소의 현재 사슬은 이렇다.

```
<base> -> 53df4c2132fd   v2 wire schema baseline
       -> a2f4c6e8d0b1   v2 continuous aggregates
       -> d1c8b4a6e2f9   reproduction 재현 서술자 컬럼 추가
       -> 1457793ebdae   Windows ProductName 원문 컬럼 추가
       -> f6f365fd114c   b3 server_metrics_5m mem byte gauges   <- head
```

`head` 는 사슬의 끝이다. 빈 DB 에 `upgrade head` 를 하면 다섯 개가 순서대로 실행되고, 세 번째까지 적용된 DB 에 같은 명령을 하면 나머지 두 개만 실행된다.

브랜치가 갈리면 head 가 둘이 된다. 두 사람이 같은 부모에서 각자 리비전을 만들면 그렇게 되고, 그때는 병합 리비전을 만들어 하나로 합쳐야 한다.

## 4. 자주 쓰는 명령

호스트에서 직접 돌릴 때는 설정 파일 위치를 환경변수로 준다. 한 번 export 해두면 이후 명령에는 붙이지 않아도 된다.

```bash
export ALEMBIC_CONFIG=src/assessment_engine/_alembic.ini

uv run alembic history          # 리비전 사슬 (DB 연결 불필요)
uv run alembic heads            # 사슬의 끝 (DB 연결 불필요)
uv run alembic current          # 이 DB 가 현재 어디까지 왔나
uv run alembic upgrade head     # 누락분 전부 적용
uv run alembic downgrade -1     # 한 단계 되돌리기
```

컨테이너로 돌릴 때는 migrate 서비스가 설정 경로를 이미 갖고 있어 그냥 명령만 바꿔 쓴다.

```bash
docker compose run --rm migrate alembic current
docker compose run --rm migrate alembic upgrade head --sql   # 실행 없이 SQL 만 출력
```

모델을 바꾼 뒤 리비전을 만들 때는 자동 생성으로 초안을 뽑고 반드시 읽어본다.

```bash
uv run alembic revision --autogenerate -m "설명"
```

자동 생성이 놓치거나 잘못 잡는 것이 있다. 컬럼 추가·삭제·타입 변경은 잘 잡지만, 인덱스 이름 변경을 drop 후 create 로 풀거나, TimescaleDB 의 hypertable·continuous aggregate 처럼 확장이 만든 객체를 모델에 없는 것으로 보고 삭제하려 든다. 그래서 생성된 파일을 그대로 커밋하지 않고 손으로 확인한다.

## 5. 이 저장소의 파일 위치

설정 파일과 리비전 디렉토리가 프로젝트 루트가 아니라 파이썬 패키지 안에 있다.

```
src/assessment_engine/
  _alembic.ini
  migrations/
    env.py
    versions/*.py
```

`alembic init` 을 돌리면 루트에 만들어지므로 이 모양이 낯설 수 있다. 기본값이 루트인 이유는 Alembic 이 "개발자가 자기 머신에서 실행하는 도구" 를 기본 가정으로 삼기 때문이다. 그 가정에서는 현재 디렉토리가 곧 프로젝트 루트다.

이 프로젝트는 실행 주체가 다르다. 마이그레이션은 배포된 컨테이너가 실행한다 — 앱 컨테이너들보다 먼저 뜨는 일회성 컨테이너가 `alembic upgrade head` 를 돌리고 정상 종료해야 나머지가 기동한다. 그 컨테이너는 앱과 같은 이미지를 쓴다. 따라서 마이그레이션이 이미지 안에 있어야 한다.

여기까지가 "아티팩트에 포함" 이고, "패키지 안" 은 그 다음 선택이다. 아티팩트에 넣는 방법이 셋인데 대가가 다르다.

루트에 두고 Dockerfile 에서 복사하면 이미지에는 들어간다. 그런데 이 프로젝트의 Dockerfile 은 최종 이미지에 가상환경만 복사하고 소스 트리를 남기지 않는다. 복사 지시를 추가하면 그 구조가 깨지고, 더 큰 문제로 wheel 에는 들어가지 않는다. CI 가 wheel 도 만들기 때문에 같은 소스에서 나온 두 산출물이 서로 다른 것을 담게 된다.

루트에 두고 빌드 백엔드 설정으로 wheel 에 밀어 넣을 수도 있다. 이때 리비전 디렉토리가 wheel 의 최상위로 들어가서, 설치하면 site-packages 바로 아래에 `migrations` 라는 흔한 이름의 디렉토리가 생긴다. 다른 패키지가 같은 이름을 쓰면 충돌한다. 패키지 안에 두면 이름이 `assessment_engine.migrations` 로 격리된다.

패키지 안에 두면 포장 설정 자체가 필요 없다. 빌드 백엔드가 패키지 디렉토리를 통째로 담으므로 확장자와 무관하게 따라 들어간다. 실제로 이 저장소의 빌드 설정에는 포함 규칙이 한 줄도 없다.

런타임 접근도 달라진다. 패키지 안에 있으면 설치 위치가 어디든 파이썬이 그 패키지를 찾는 방식으로 함께 찾을 수 있다. 루트 배치는 현재 디렉토리를 기준으로 삼는데, 설치된 환경에는 그 기준점이 없다.

대가는 두 가지다. 호스트에서 명령을 돌릴 때 설정 경로를 알려줘야 하고(위의 `ALEMBIC_CONFIG`), `alembic init` 직후 모양과 달라 처음 보면 낯설다. 설정 파일 이름 앞의 밑줄은 "패키지 내부 자원이니 직접 열지 말라" 는 표시다.

## 6. 이 저장소에서 지키는 것

리비전 디렉토리 위치는 설정 파일 기준 상대 경로로 적혀 있다. 어느 디렉토리에서 명령을 돌려도 같은 곳을 가리킨다.

DB 접속 주소는 설정 파일에 비어 있고 `env.py` 가 애플리케이션 설정에서 읽어 넣는다. 접속 정보가 파일에 평문으로 남지 않고, 앱과 마이그레이션이 같은 환경변수 정책을 쓴다.

새 리비전을 만들면 모델 변경과 같은 커밋에 넣는다. 둘이 갈라지면 어느 시점의 코드가 어느 스키마를 전제하는지 알 수 없게 된다.

되돌리기(`downgrade`)는 작성하되 운영에서 실행하지 않는 것을 전제로 둔다. 배포 실패 시 이미지는 이전 버전으로 돌아가지만 스키마는 그대로 남는다. 그래서 새 스키마에서 구버전 코드가 동작할 수 있게 변경을 설계한다 — 컬럼을 지우는 대신 쓰지 않는 상태로 두고, 필요하면 다음 릴리즈에서 제거하는 식이다.
