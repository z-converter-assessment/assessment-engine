# collect 경로 리뷰 노트

임시 자료 — 내부 학습 전용, 외부 공유 대상 아님, 삭제 자유. 리뷰가 끝나 코드 수정과 영구 문서 반영이 완료되면 삭제한다.

## 목적과 범위

본 엔진 코드를 교재로 파이썬을 익히면서, 동시에 코드 결함을 찾아 수정하는 것이 목적이다. 두 목적이 같은 순서를 공유한다 — 흐름을 따라 읽으면 파이썬 관용구와 결함이 같은 자리에서 드러난다.

범위는 에이전트에서 엔진으로 들어오는 수집 경로 한 줄기다. 메시지 계약에서 시작해 DB INSERT까지 끝낸다. 표현 계층(웹·보고서·right-sizing)과 발신 경로(task.install)는 범위 밖이다.

범위를 이렇게 자른 근거는 계약이 시스템의 최상위 제약이라는 점이다. 수집 경로의 모든 코드는 계약의 구현이고, 저장된 데이터의 형태가 이후 모든 표현 계층의 입력을 정한다. 계약을 모르는 상태로 표현 계층을 읽으면 왜 그 필드가 그 타입인지 판단할 근거가 없다.

## 수집 경로 지도

```
agent (customer internal network)
  |  AMQP publish
  |  routing key: server.inventory / server.metrics / agent.error / task.result
  v
consumer bootstrap
  |  exchange + queue declare, DLX bind, prefetch 10
  |  handler = closure factory (captures session_factory, repo class, redis)
  v
message handler (one per routing key)
  |  1. Pydantic model_validate_json()   <- the ONLY validation point
  |  2. idempotency check (Redis SET NX, fail-open)
  |  3. mapper: wire payload -> flat storage DTO
  |  4. post-processing (online marker, cache invalidation, signal logs)
  v
collect repository
  |  pg_insert(...).on_conflict_do_nothing()  <- 2nd idempotency layer
  v
TimescaleDB: host aggregate table + 6 child timeseries tables
```

메시지는 4종이다 — inventory(정적 인벤토리), metrics(시계열 메트릭), error(에이전트 자기 진단), task.result(설치 작업 결과). 앞의 3종은 수집 exchange, task.result는 별도 task exchange를 쓴다.

멱등성은 2단이다. 1단은 Redis `SET NX`로 동일 message_id 재전송을 차단하고, Redis 장애 시에는 통과시킨다(fail-open). 2단은 시계열 테이블의 자연키 UNIQUE 제약과 `ON CONFLICT DO NOTHING`이 중복 INSERT를 조용히 흡수한다. 1단이 깨져도 2단이 받는 구조이므로 자연키 UNIQUE는 보존 의무 대상이다.

## 리뷰 순서

한 세션은 코드 100~250줄, 파이썬 주제 3~5개로 맞춘다.

처음 들어가는 영역은 구성 요소 전체를 먼저 펼친 뒤 상세로 내려간다. 용어를 마주칠 때마다 하나씩 설명하면 그 설명이 또 모르는 용어를 물고 와서 진도가 나가지 않는다. 지도를 먼저 그리고 그 위에 코드를 놓는다.

한 세션 안에서 읽기와 수정을 모두 끝낸다. 그 계층에서 문제를 발견하면 그 자리에서 결정하고 고치며, 다음 세션으로 미루지 않는다. 방금 읽은 맥락이 살아 있을 때가 가장 정확하고, 세션이 닫힐 때마다 그 계층에 미결이 없다는 상태가 유지된다.

세션 진행 중에는 코드와 본 노트만 건드린다. 영구 문서 동기화는 세션이 닫힐 때 확정된 코드를 보고 한 번에 처리하며, 코드 변경이 계약이나 규약의 서술을 바꾸는 경우에만 해당한다. 수정할 때마다 문서를 따라 고치면 세션 안에서 코드가 다시 바뀔 때 같은 문단을 여러 번 쓰게 된다. 커밋은 세션마다 하나씩 끊어 각 커밋이 한 계층의 리뷰와 수정으로 자족하게 한다.

| 세션 | 대상 | 파이썬 주제 | 상태 |
|------|------|------------|------|
| S1 | 계약 문서와 JSON Schema, 계약 버전 상수 | (코드 아님) | 미착수 — 이슈 1 담당 |
| S2 | 인바운드 wire 스키마 모듈 | Pydantic v2 모델, Literal, alias, field_validator | 완료 |
| S3 | 컨슈머 부트스트랩 + inventory 핸들러 | asyncio 이벤트 루프, 시그널 핸들러, 클로저 팩토리 DI, async with | 미착수 |
| S4 | 핸들러 공통 helper | PEP 695 제네릭 함수, 예외 계층 분류, 지수 백오프, 안전한 getattr 체인 | 미착수 |
| S5 | 매퍼 metrics 절반 | 임의 kwargs, 제너레이터 표현식과 all(), dict를 순서 있는 집합으로 쓰기 | 미착수 — 이슈 2 담당 |
| S6 | 매퍼 inventory 절반 + 인바운드 DTO | dataclass, default_factory, dict unpacking, 조건부 키 병합 | 미착수 |
| S7 | collect 리포지토리 + 시계열 모델 자연키 | SQLAlchemy Core, staticmethod와 클래스 변수, vars() 대 asdict() | 미착수 — 이슈 3 담당 |
| S8 | metrics 핸들러 + task.result 핸들러 + error 핸들러 | 중첩 코루틴, 튜플 반환 언패킹, lambda 훅 | 미착수 |

순서 근거는 4가지다.

계약을 코드보다 먼저 읽는다(S1 -> S2). 스키마 모듈의 필드 선언 하나하나가 계약 조항의 번역이므로, 원문을 모르면 번역의 정확도를 검증할 수 없다. S2가 먼저 끝난 상태이므로 S1은 사후 검증 역할을 겸한다.

가장 단순한 핸들러로 골격을 먼저 잡는다(S3). inventory 핸들러는 47줄이고 분기가 없어서 4단계 처리 흐름이 그대로 보인다. metrics 핸들러는 미등록 서버 자동 등록과 placeholder 경합 처리가 얽혀 있어서 리포지토리를 알기 전에는 읽을 수 없다 — 그래서 S8로 미룬다.

변환을 저장보다 먼저 읽는다(S5·S6 -> S7). 매퍼의 출력 DTO가 곧 리포지토리의 입력이고, 리포지토리는 DTO 필드명을 컬럼명으로 그대로 쓴다. 이 결합을 알고 리포지토리를 봐야 한다.

발견한 문제는 그 문제를 담당하는 계층의 세션에서 닫는다. 이미 나온 이슈 3건도 각자 자기 계층의 세션에 배정되어 있어서 별도 수정 세션이 필요하지 않다.

## 세션 기록

### S2 — 인바운드 wire 스키마 (완료)

계약을 파이썬 타입 시스템으로 표현한 계층이다. Pydantic v2 모델 하나가 메시지 1종에 대응한다. 배운 문법 6개를 정리한다.

타입 자체를 게이트로 쓴다. `Literal["1.0"]`, `Literal["counter", "gauge"]`처럼 값 집합을 타입으로 선언하면 별도 검증 코드가 필요 없다. 위반 시 `ValidationError`가 나고, 핸들러가 그것을 그대로 raise 하면 메시지 처리 컨텍스트가 nack 해서 dead letter queue로 보낸다. 검증 로직과 실패 처리가 분리된다.

required-nullable과 optional을 구분한다. 이 파일에서 가장 중요한 디테일이다.

```python
# 키 필수, 값은 null 허용 (default 없음)
system_cpu: Namespace | None = Field(alias="system.cpu")

# 키 자체가 없어도 됨 (default=None)
system_paging: Namespace | None = Field(default=None, alias="system.paging")
```

어노테이션은 둘 다 `Namespace | None`으로 같지만 의미가 다르다. `Field()`에 default가 있으면 optional, 없으면 required다. `| None`은 값으로 null이 올 수 있다는 뜻이고 키의 존재 여부와는 무관하다. 계약상 필수 네임스페이스는 키가 반드시 있어야 하고 값이 null이면 그 네임스페이스 전체 미지원을 뜻한다 — 이 구분이 필드 선언 하나로 표현된다.

alias로 파이썬 식별자가 될 수 없는 키를 받는다. `system.cpu`는 점이 들어가 속성명이 못 되므로 `Field(alias=...)`로 JSON 키와 필드명을 분리한다. 모델 설정의 `populate_by_name=True`는 alias 외에 필드명으로도 채우게 허용해서 테스트에서 dict를 직접 구성할 때 편하다.

validator의 `mode="before"`는 타입 변환 전 원본 값을 받는다. 기본값인 `mode="after"`는 이미 타입이 확정된 뒤라서, 리스트 원소를 하나씩 검사해야 하는 경우에는 before가 필수다. 데코레이터 순서는 `@field_validator`가 위, `@classmethod`가 아래다 — 데코레이터는 아래에서 위로 적용되므로 field_validator가 classmethod 객체를 받아야 한다.

검증만 하고 값은 원본 그대로 반환하는 패턴이 있다.

```python
ip_address(str(v))  # 형식 위반이면 ValueError, 아니면
return v            # 원본 문자열 그대로
```

`ip_address()`를 부작용(예외 발생)만 목적으로 호출하고 결과를 버린다. 저장은 raw 문자열로 하고 검증만 진입점에서 한 번 한다는 원칙의 구현이다.

가변 기본값은 `Field(default_factory=dict)`로 만든다. `= {}`로 쓰면 클래스 정의 시점의 dict 하나를 전 인스턴스가 공유하는 함정에 빠진다. Pydantic은 내부적으로 deep copy 해서 막아주지만 dataclass에서는 실제 에러가 나므로 습관을 통일한다.

## 실행 검증 대기 목록

리뷰는 정적 읽기로 진행한다. 코드 구조와 계약 정합은 실행이 새 정보를 주지 않고, 돌아가는 경로만 보면 Windows 분기나 값이 null인 경계처럼 testbed에 조건이 없는 경로를 놓친다. 저장 계층은 통합 테스트가 실제 시계열 DB 컨테이너를 띄우므로 별도 환경 없이 확인된다.

실행으로만 확정되는 질문은 여기에 쌓고 리뷰가 끝난 뒤 한 번에 검증한다.

| 질문 | 확인 방법 | 나온 세션 |
|------|----------|-----------|
| 에이전트가 실제 emit 하는 datapoint attr 값의 타입 | 실 환경 메시지 캡처 | S0 |
| 계약 예시가 현재 에이전트 버전의 emit과 여전히 일치하는지 | 실 환경 메시지와 예시 파일 대조 | S0 |

### 이슈 1 — 버전 게이트 정책과 구현 불일치

정책은 "major 완전 일치, minor silent 호환"으로 확정했다. 계약과 구현을 이 정책에 맞춘다.

S1에서 정본을 확인한 결과 초기 진단이 뒤집혔다. 정본인 wire JSON Schema는 버전을 `const "1.0"`으로 규정해 minor를 허용하지 않는다. 인바운드 Pydantic 모델의 `Literal["1.0"]`은 이 정본과 정합하며, 어긋나 있는 것은 산문 서술 세 곳이다 — 계약 버전 상수 파일의 모듈 docstring, 계약 문서 본문의 게이트 서술, 보고서 템플릿의 에이전트 계약 참조 표. 계약 문서는 스스로 스키마를 정본으로 선언하고 어긋나면 스키마가 이긴다고 정하므로, 코드가 아니라 서술이 틀린 상태다. 계약 문서 안에서도 버전을 고정으로 서술한 줄과 major만 비교한다고 서술한 줄이 충돌한다.

현행 계약을 유지하면 `major.minor` 형식과 "minor는 additive 변경 추적용"이라는 정의가 문서에만 남고 실제로는 쓸 수 없는 개념이 된다. 에이전트가 필드 추가로 minor를 올리는 순간 모든 메시지가 검증 실패로 dead letter queue에 쌓인다.

수정 범위는 계약 자체를 포함한다.

- wire JSON Schema의 버전 규정을 `const`에서 major 일치 패턴으로 변경
- 계약 문서에서 버전을 고정으로 서술한 줄을 정정
- 인바운드 모델의 `Literal`을 문자열 + major 비교 validator로 변경
- 에이전트 팀에 계약 변경 통보

변경 방향이 완화라서 에이전트 측 코드 수정은 필요 없다. 지금처럼 `"1.0"`을 계속 발행하면 되고, 이후 필드 추가 시 minor를 올릴 여지가 생긴다.

### 이슈 2 — attr 값 타입 permissive superset 미대응

계약은 datapoint의 attr 값 타입을 문자열과 숫자 둘 다 허용하고, 인바운드 모델도 `dict[str, str | int]`로 그 superset을 받는다. 그런데 매퍼는 문자열만 전제한다. 차원 값을 수집하는 헬퍼가 `isinstance(v, str)`로 필터하고, 매칭 헬퍼는 `attr.get(k) == v`로 비교하므로 `0 == "0"`이 False가 된다.

영향 범위는 이렇다.

| 숫자로 오는 attr | 결과 |
|------------------|------|
| cpu | per-core 시계열 전체 유실 |
| device | 디스크 I/O, 네트워크 I/O 축 전체 유실 |
| window | PSI 비율 3개 컬럼 전부 null |

현재 에이전트는 코어 인덱스와 윈도우를 문자열로 emit 하고 있어 무증상이다. 계약이 열어 둔 축이고, 조용히 데이터가 사라지는 실패 모드라 발견이 늦다. 두 헬퍼에서 `str()` 정규화로 막힌다.

### 이슈 6 — 독립적으로 진화하는 계약들이 버전 하나를 공유

버전 상수 하나가 네 계약을 덮는다 — 에이전트가 보내는 메시지(wire), 엔진이 에이전트에 보내는 설치 명령, 외부 시스템에 나가는 평가 API 응답, 그리고 그 응답 구조를 재사용하는 export 파일이다. 상수를 참조하는 코드는 설치 명령 발행과 평가 API 응답 두 곳이고, 메시지 수신 게이트는 타입 표현식 제약 때문에 값을 직접 박아 두었다.

통일 버전은 세 주체를 동시에 전환할 수 있다는 전제 위에 선다. 그 전제는 성립하지 않는다 — 에이전트가 고객사 내부망에 분산되어 있어 동시 전환이 불가능하다는 사실은 이 프로젝트가 이미 인정하고 있고, 그래서 인바운드 모델이 모르는 필드를 통과시켜 부분 배포 비대칭을 흡수한다. 같은 계약 체계가 한쪽에서는 비대칭 배포를, 다른 쪽에서는 동시 전환을 전제한다.

세 계약은 각자 다른 이유로 바뀌므로 공유 버전에서 세 가지 사고가 나온다.

메시지 계약의 구조 변경으로 major를 올리면 아무것도 바뀌지 않은 평가 API 응답의 버전도 함께 올라, 외부 시스템이 대응 여부를 판단하게 만드는 거짓 신호가 된다. 평가 API에 필드가 추가되어 minor가 오르면 에이전트가 받는 설치 명령의 버전도 따라 올라 추적 정보가 오염된다. 가장 위험한 것은 평가 API의 구조 변경으로 major가 오를 때다 — 에이전트는 모르는 major의 설치 명령을 실행 전에 거부하므로, 외부 시스템 쪽 사정으로 바뀐 번호 때문에 설치 기능이 전면 중단된다.

수정은 상대 기준으로 둘로 나누는 것이다. 에이전트와 주고받는 계약(메시지 + 설치 명령)이 하나, 외부 시스템에 나가는 계약(평가 API + export)이 하나다. 메시지와 설치 명령은 같은 에이전트가 양방향으로 쓰고 결과 보고가 명령과 짝을 이루므로 함께 움직이는 편이 자연스럽고, export는 평가 API의 구조를 그대로 쓰므로 독립 버전이 무의미하다.

현재 값은 둘 다 그대로 두면 외부에 나가는 값이 바뀌지 않는다. 아직 버전을 올린 이력이 없어 과거 번호의 의미를 계약별로 소급 해석할 문제도 없다 — 한 번이라도 올린 뒤에는 이 분리가 비싸진다.

### 이슈 5 — 검증 실패 로그가 진단에 쓸모없음

메시지 핸들러 4개가 모두 같은 형태로 검증 실패를 처리한다. 로그에 에러 개수만 남기고 예외를 다시 던진다. 원인이 된 필드도, 에러 종류도 남지 않는다.

에이전트 새 버전 배포 직후 메트릭이 전부 dead letter queue로 가는 상황을 가정하면, 로그에는 개수 1이 수천 줄 쌓이고 운영자는 어느 필드가 거부됐는지 알 수 없어 큐에서 메시지를 꺼내 눈으로 봐야 한다.

원인은 페이로드 노출 금지 규약을 지키려다 정보를 전부 버린 것이다. 검증 오류 객체는 필드 경로와 에러 종류를 실제 값과 분리해 제공하므로, 앞의 둘만 남기면 페이로드 내용을 노출하지 않으면서 원인이 특정된다. 원본 메시지는 dead letter queue에 보존되므로 로그는 어디를 볼지만 가리키면 된다.

### 이슈 4 — 정본 JSON Schema가 강제력이 없음

계약 정본이 4개다 — 계약 문서의 필드 표, wire JSON Schema, 인바운드 Pydantic 모델, 에이전트 C 소스. 네 개를 손으로 동기화한다.

이 중 JSON Schema만 기계가 읽을 수 있는 형식인데도 읽는 코드가 없다. 테스트 docstring에서 정본으로 선언되지만 파일을 로드하지 않고, JSON Schema 검증 라이브러리도 개발 의존성에 없다. 실제로 강제되는 것은 Pydantic 모델뿐이다. 빠진 게이트가 둘이다 — 계약 예시가 JSON Schema를 만족하는지 검사하지 않고, JSON Schema가 허용한다고 규정한 값을 Pydantic이 실제로 수용하는지도 검사하지 않는다.

이슈 1과 이슈 2가 모두 이 구조의 결과다. 둘 다 JSON Schema는 A라고 규정하는데 Pydantic이 B를 하는 형태다.

JSON Schema를 Pydantic 생성물로 강등하는 방향은 실측 결과 부적합하다. 손으로 쓴 스키마는 `allOf`/`if-then`으로 메시지 4종을 한 파일에 담고 `$comment` 43개로 계약 규칙을 서술한다 — 부모 참조가 불안정한 이름이 아니라 안정 id라는 것, 안정 id의 폴백 계층 같은 설명은 타입 선언만으로 전달되지 않는다. Pydantic 자동 생성물은 모델별 4개로 분할되고 설명이 전부 빠지며, 같은 설명을 살리려면 `Field(description=...)`으로 43곳을 옮겨야 한다. 이 스키마는 에이전트 개발자가 읽는 계약 문서를 겸하므로 사람이 쓰는 정본으로 유지한다.

수정 방향은 JSON Schema를 정본으로 유지하고 검사를 붙이는 것이다. 게이트가 둘이다.

첫째는 계약 예시가 JSON Schema를 만족하는지 검사한다. JSON Schema 검증 라이브러리를 개발 의존성에 추가하고 테스트 하나를 붙인다.

둘째는 스키마가 허용한다고 규정한 값을 Pydantic이 수용하는지 검사한다. 두 정본은 구조가 달라 직접 비교가 안 되므로 예시 파일을 공통 증인으로 쓴다. 현재 예시 6종은 정상 경로만 담아서 이슈 1과 2를 통과시켰다 — attr 값이 숫자인 예시가 없고 minor 버전이 다른 예시도 없다. 경계 케이스 fixture를 추가해 두 정본 양쪽으로 검증하면 두 이슈가 CI에서 재발 차단된다.

### 이슈 3 — 충돌 대상 없는 DO NOTHING

멱등성 2단 방어 규약은 `on_conflict_do_nothing(index_elements=...)`로 충돌 대상을 명시하도록 정한다. 자식 시계열 bulk INSERT는 인자 없이 호출하므로 그 테이블의 모든 unique 제약 위반을 함께 삼킨다. 현재 스키마에서는 오동작으로 이어지지 않지만, 제약이 추가되면 의도 밖 충돌을 조용히 무시한다. 같은 파일의 호스트 집계 INSERT는 대상을 지정하고 있어서 한 파일 안에서 스타일이 갈린다.
