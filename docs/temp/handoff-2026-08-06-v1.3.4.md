## 다시 시작하지 말 것

`.github/dependabot.yml` 을 되살리지 말 것. 자동 갱신 PR 을 끄는 것이 정책이고, 파일이 있으면
version updates 가 토글과 무관하게 발화한다. 갱신은 사유가 있을 때 사람이 한다.

Dependabot alerts 는 켜 둔 상태다 (자동 PR 과 별개 토글). 이것까지 끄면 "사유가 있을 때만 갱신" 이
"영원히 안 함" 이 된다.

런타임 이미지의 pip 제거를 되돌리지 말 것. 베이스가 딸려 보내는 것이라 무해해 보이지만, 이번에 나온
취약점 2건(msgpack·setuptools)의 출처가 전부 그 vendor 트리였다. 애플리케이션은 `/opt/venv` 만 쓰고
그 venv 가 `include-system-site-packages=false` 라 pip 을 아예 보지 않는다.

`_action` 의 목표 키를 자원별 분기로 편 것을 `_TARGET_KEY` dict 로 되돌리지 말 것. 변수 키 대입
(`a[key] = v`)은 pyright 가 검사하지 못해 TypedDict 전환의 이득이 그 자리에서만 사라진다. 짧아 보여서
되돌리기 쉬운 형태다.

의식적으로 유예한 설계는 `docs/explanation/tradeoffs.md` T24 (`disk_baseline` 을 보고서 경로에만 주입).
통일하면 화면 분류가 실제로 바뀌므로 계약 개정 절차가 필요하다.

## 알아 둘 함정

`image-scan` 은 이번 승격으로 처음 활성화됐다. 수동 실행으로 전 구간(trivy -> SARIF -> Security 탭
`image-os-packages` category)이 도는 것까지 확인했다. 다만 schedule 워크플로는 기본 브랜치에서만 발화하고
`workflow_dispatch` 도 같은 제약을 받으므로, 이 워크플로를 고치면 main 에 올라가기 전에는 시험할 수 없다.

GitHub 은 public repo 에 60일간 활동이 없으면 schedule 워크플로를 자동 비활성화한다. 버전 고정 정책이
조용한 저장소를 전제하므로 이 채널은 가장 필요한 국면에서 멈출 수 있다. 릴리즈 간격이 두 달을 넘기면
Actions 탭에서 마지막 `image-scan` 실행 시각을 본다.

develop -> main 승격 PR 에서는 check 이름이 중복으로 보인다. develop 머지 직후 검증(push 이벤트)과
승격 PR 검증(pull_request 이벤트)이 같은 SHA 에 붙기 때문이고, `pytest (integration)` 이 pass 와 skipping
으로 동시에 뜬다. 1.3.4 승격에서 `mergeStateStatus=CLEAN` 으로 정상 통과하는 것을 확인했다.

HTTP 스냅샷은 화면 구조만 지킨다. 엔진 버전·`?v=` 토큰·발행 시각은 정규화로 지운다. 버전이 화면에
찍히는지 자체는 `test_engine_version_is_rendered` 가 따로 본다.

차트 페이지 스크린샷은 결정적이지 않다. 같은 코드를 두 번 찍어도 20px 시각 표시 밴드가 흔들린다.
픽셀 대조할 때는 "before-after 차이" 를 "after-after 차이" 와 비교해야 판단이 선다.

`alembic check` 는 DB 가 있어야 돈다. 로컬에서 그냥 부르면 Settings 검증에서 먼저 죽는다. 검증은
`alembic-check.yml` 잡이나 통합 테스트(testcontainers)가 맡는다.

## 정리 대상 브랜치 — 판단만 해 두고 손대지 않았다

원격 브랜치를 지우는 것은 되돌리기 어려운 공유 자원 변경이라, 확인만 하고 삭제는 남겨 둔다.

| 브랜치 | PR | 내용이 develop 에 |
|--------|-----|------------------|
| `origin/feature/new` | #159 CLOSED (머지 아님) | 있다 — `response_model=` 제거가 반영돼 있다 |
| `origin/test/pytest-config` | #160 CLOSED (머지 아님) | 있다 — `asyncio_mode`·`filterwarnings` 가 반영돼 있다 |
| 로컬 `refactor/self-type` | PR 없음 | 확인 안 함 |

둘 다 PR 이 머지가 아니라 CLOSE 됐고, 같은 변경이 뒤 브랜치를 통해 develop 에 다시 들어왔다. 그래서
커밋 해시는 develop 조상이 아니지만 내용은 남아 있다. 지워도 잃는 것이 없다고 판단하나, 확인 후 지운다.

## 검토했으나 손대지 않은 것

불필요한 로직 전수 조사를 13축으로 돌렸고 실질 제거 대상은 dependabot 하나였다. Settings 필드 60개·
Redis 키 17개·public 함수 227개·ViewModel 필드 880개·템플릿 38개·JS 24개 모두 미사용 0건이다.
후보로 뜬 것들은 전부 오탐이었다 — 라우트 핸들러는 데코레이터 등록이라 이름 호출이 없고, Settings 는
`config.py` 안에서 URL 조립에 쓰인다.

판단이 필요한 수준은 아니지만 참조가 0인 것 둘이 남아 있다. `make test-http` 는 명령이 유효한데 문서가
안 가리키고, `pnpm typecheck:watch` 는 편집 중 감시용이라 참조가 없는 게 정상이다. 둘 다 두는 것으로 봤다.

secret scanning 의 validity checks 는 켜지지 않는다. PATCH 를 200 으로 받고도 값이 disabled 로 남아
이 저장소 플랜에서 안 되는 것으로 보고 비활성으로 기록했다. non-provider patterns 는 오탐 때문에 의도적으로 껐다.
