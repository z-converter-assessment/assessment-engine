# 파이썬 패키징 지도

임시 자료 — 내부 학습 전용, 외부 공유 대상 아님, 삭제 자유.

패키징 용어는 서로를 전제하며 정의되어서, 하나씩 마주칠 때마다 배우면 매번 모르는 단어가 딸려 나온다. 전체 구조를 다섯 층으로 먼저 세우고 각 층에 용어를 배치한다.

## 1층. 파이썬이 코드를 찾는 방법

`import assessment_engine` 을 만나면 파이썬은 `sys.path` 라는 디렉토리 목록을 순서대로 뒤진다. 그 안에서 같은 이름의 디렉토리나 파일을 찾으면 읽고, 끝까지 없으면 `ModuleNotFoundError` 를 낸다.

`site-packages` 는 그 목록에 기본으로 들어 있는 디렉토리다. 설치된 패키지가 놓이는 표준 위치이며, 이름 그대로 이 설치본(site)의 패키지들이라는 뜻이다.

이 층에서 기억할 것은 하나다. 코드가 디스크 어딘가에 있다는 사실만으로는 import 되지 않는다. `sys.path` 안에 있어야 한다.

## 2층. 그 위치에 코드를 놓는 것 — 설치

설치란 `site-packages` 에 파일을 놓는 작업이다. 실행과는 무관하다. 설치는 배치이고, 실행은 그 뒤에 별도로 일어난다.

놓는 방식이 둘이다.

일반 설치는 파일을 실제로 복사한다. 원본 소스를 지워도 동작하고, 원본을 고쳐도 반영되지 않는다. 배포용이다.

editable 설치는 경로가 적힌 `.pth` 파일 하나만 놓는다. 파이썬이 시작할 때 그 경로를 `sys.path` 에 추가하므로 원본 소스를 직접 읽는다. 소스를 고치면 재설치 없이 반영된다. 개발용이다.

## 3층. 설치할 것을 만드는 것 — 빌드

소스 디렉토리를 그대로 복사하지 않는다. 표준 형식으로 포장한 뒤 그것을 푼다. 포장 형식이 둘이다.

sdist(`.tar.gz`)는 소스와 빌드 설정을 담는다. 설치하려면 받는 쪽에서 빌드해야 한다.

wheel(`.whl`)은 이미 빌드된 결과다. 압축을 풀어 복사하면 설치가 끝난다.

어떤 경로로 설치하든 마지막 단계는 wheel 을 푸는 것이다. 원격에 wheel 이 있으면 받아서 쓰고, sdist 만 있거나 로컬 소스면 그 자리에서 wheel 을 만들어 쓴다.

wheel 파일명은 호환 범위를 담는다. `이름-버전-파이썬태그-ABI태그-플랫폼태그.whl` 형식이며, 순수 파이썬 패키지는 `py3-none-any` 처럼 제약이 없고, C 나 Rust 확장을 포함하면 `cp312-cp312-manylinux_2_17_x86_64` 처럼 인터프리터와 플랫폼이 박힌다. 확장을 포함한 패키지가 플랫폼별 wheel 을 미리 올려두기 때문에 설치하는 쪽에 컴파일러가 없어도 된다.

포장하는 프로그램을 빌드 백엔드라고 한다. hatchling, setuptools, poetry-core, flit 이 있고 어느 것을 쓸지는 `pyproject.toml` 의 `[build-system]` 이 정한다.

빌드를 시키는 쪽은 빌드 프론트엔드다. pip, uv, build 가 그것이다. 프론트엔드가 백엔드를 호출해 wheel 을 만들게 하고, 나온 wheel 을 설치한다.

버전도 이 층에서 정해진다. `pyproject.toml` 에 값을 직접 적는 것이 기본이고, 플러그인을 붙여 버전 관리 시스템에서 derive 할 수도 있다. hatch-vcs 가 그런 플러그인으로, 마지막 태그와 그 뒤 커밋 수로 버전을 만든다. 버전을 올리는 커밋이 필요 없어지고 태그가 유일한 출처가 되는 대신, 빌드하는 자리에 저장소 이력이 있어야 한다.

## 4층. 무엇을 설치할지 정하는 것 — 의존성

`pyproject.toml` 에 필요한 패키지를 범위로 적는다. 범위만 있으면 설치 시점마다 다른 버전이 잡히므로, lock 파일에 이번에 실제로 고른 버전과 해시를 박아둔다. 재현성을 담당하는 층이다.

lock 파일 형식은 도구마다 다르다. uv 는 `uv.lock` 을 쓰며 이는 uv 전용 포맷이라 pip 이 읽지 못한다. pip 이 읽는 표준은 requirements 형식이고, 둘 사이는 export 명령으로 번역한다.

## 5층. 환경을 격리하는 것 — 가상환경

프로젝트마다 필요한 버전이 다른데 `site-packages` 가 하나뿐이면 충돌한다. 가상환경은 프로젝트 전용 `site-packages` 를 따로 만드는 장치다. 디렉토리 하나 안에 인터프리터 링크와 전용 `site-packages`, 실행 스크립트를 두는 `bin` 이 들어간다.

`bin` 안 스크립트에는 인터프리터 절대경로가 shebang 으로 박힌다. 그래서 가상환경 디렉토리를 다른 경로로 옮기면 그 스크립트들이 깨진다.

## 흔한 혼동

설치와 실행은 다르다. 설치는 코드를 import 가능한 위치에 놓는 것이고, 실행은 그 뒤 인터프리터가 코드를 돌리는 것이다.

wheel 을 쓴다는 말은 wheel 파일을 손으로 다룬다는 뜻이 아니다. 어떤 설치 명령이든 내부적으로 wheel 을 만들거나 받아서 푼다. 명시적으로 파일을 만드느냐 도구에 맡기느냐의 차이만 있다.

가상환경 안에서도 표준 위치는 여전히 `site-packages` 다. 위치가 시스템 전역이 아니라 프로젝트 디렉토리 아래로 옮겨진 것뿐이다.

## 이 프로젝트의 배치

| 층 | 채택 |
|----|------|
| 1 | 소스를 `src/` 아래 두는 배치 — 설치하지 않으면 import 되지 않음 |
| 2 | 개발은 editable, 컨테이너는 `--no-editable` 복사 설치 |
| 3 | 빌드 백엔드 `uv_build`, 버전은 `pyproject.toml` 에 직접 적고 `uv version` 으로 올림 |
| 4 | `pyproject.toml` 범위 선언 + `uv.lock` 고정 |
| 5 | 개발과 컨테이너 모두 가상환경 사용 |

컨테이너 이미지를 만드는 과정을 이 지도로 옮기면 한 문장이 된다. 4층의 lock 을 읽어 5층의 가상환경 안에 3층의 wheel 들을 2층 방식으로 설치해서 1층의 import 가 성립하는 상태를 만들고, 그 가상환경 디렉토리만 최종 이미지로 옮긴다.
