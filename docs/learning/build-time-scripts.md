# 빌드 시점 도구와 커밋되는 생성물

학습 자료. 기준 시점 2026-08-03, 커밋 `7a0e4ec`. 갱신 의무 없음.

1절이 오리엔테이션, 2절부터 4절이 L2, 5절과 6절이 L3 다.

## 1. 실행 시점으로 코드를 가른다

저장소 안의 실행 가능한 코드를 어디에 둘지는 무엇을 하느냐가 아니라 언제 도느냐가 정한다. 이 저장소는 넷으로 갈린다.

| 시점 | 어디서 도나 | 아티팩트에 들어가나 |
|------|-------------|--------------------|
| 런타임 | 컨테이너 | 이미지 안 |
| 마이그레이션 | 컨테이너, 앱보다 먼저 1회 | 이미지 안 |
| 배포 | 배포 대상 VM, 운영자가 실행 | 배포 디렉토리로 복사 |
| 개발·워크플로 | 저장소를 체크아웃한 머신 | 어디에도 안 들어감 |

앞의 둘이 무엇인지는 `docs/reference/docker.md` 가 갖는다. 마지막 칸이 `scripts/` 이고 파일 셋이 있다.

배포 시점 스크립트가 루트에 따로 있는 이유도 같은 축이다. 그쪽은 배포 디렉토리로 복사돼 나가 저장소 없이 돌아야 하므로 개발 시점 도구와 섞이면 안 된다.

## 2. 배치를 정하는 것은 실행 시점

도구가 얼마나 자주 도는지, 누가 부르는지는 배치를 정하지 않는다. 컨테이너 안에서 돌아야 하는 것만 패키지 안에 둔다.

외부 데이터를 긁어 오는 생성기를 예로 들면 갱신 주기별로 자리가 이렇게 갈린다.

| 갱신 시점 | 코드 위치 |
|-----------|-----------|
| 사람이 필요할 때 | 개발 시점 스크립트 |
| 워크플로 빌드 시점 | 개발 시점 스크립트 (러너가 체크아웃하므로) |
| 배포 시 VM 에서 | 배포 스크립트 채널 |
| 컨테이너 기동 시 또는 주기적으로 | 패키지 안 |

"배포마다 최신화하고 싶으니 소스에 넣어야 하나" 는 잘못된 갈림이다. 릴리즈 워크플로가 이미지 빌드 앞에서 돌리면 이미지마다 최신이 되고, 스크립트는 개발 시점 자리에 그대로 있는다.

생성기를 패키지 밖에 두면 얻는 게 하나 더 있다. 그 코드가 외부를 호출한다면 밖에 둠으로써 런타임 이미지에 외부 호출 코드가 아예 존재하지 않게 된다. 실행될 일이 없더라도 없는 편이 확실하다. 생성기는 밖, 산출물은 안이라는 분리다.

## 3. 생성물을 커밋할지 판단하는 기준

생성물을 커밋하지 않고 빌드마다 만드는 선택지도 있다. 커밋 쪽으로 기우는 조건이 넷이다.

- 생성 도구의 툴체인을 빌드 환경에 들이기 싫다
- 생성이 결정적이다 (같은 입력이면 같은 출력)
- 입력이 자주 바뀌지 않는다
- 생성물의 diff 가 리뷰에 의미를 준다

첫째가 보통 가장 큰 동기다. 파이썬 패키지를 만드는 데 프론트엔드 툴체인이 끌려 들어오는 식의 오염을 막는다.

둘째는 조건이 아니라 전제에 가깝다. 결정적이지 않으면 커밋본과 재생성본을 대조할 수 없고, 대조할 수 없으면 4절의 게이트를 세울 방법이 없다. 타임스탬프가 섞이는 생성기라면 커밋 자체를 재고해야 한다.

넷째는 자주 간과된다. 생성물을 커밋하지 않으면 PR diff 에 원본 변경만 보이고 그것이 계약을 어떻게 바꿨는지는 안 보인다.

## 4. 원본 위치가 게이트 가능성을 가른다

커밋한 생성물은 원본과 갈라질 수 있다. 그 갭을 막는 게이트를 세울 수 있는지는 원본이 어디 있느냐가 정한다.

원본이 저장소 안이면 게이트가 선다. 워크플로가 같은 커밋에서 재생성한 뒤 커밋본과 대조해, 다르면 실패시킨다. 다르다는 것은 곧 사람이 재생성을 빼먹었다는 뜻이므로 실패가 옳은 판정이다.

```
generator + source in the same commit
    -> regenerate in CI -> diff means the author forgot -> fail
```

원본이 저장소 밖이면 게이트가 안 선다. 재생성 결과가 달라지는 것이 정상이고, 그걸 실패로 처리하면 우리 잘못이 아닌 이유로 통합이 막힌다.

```
generator pulls from an external service
    -> regenerate -> diff is expected -> failing here blocks work for no fault
```

밖이 원본일 때 쓸 수 있는 건 실패가 아니라 알림이다. 주기 실행 워크플로가 생성기를 돌려 diff 가 생기면 이슈나 PR 을 여는 방식이면 통합을 막지 않으면서 갱신 필요만 드러난다. 그 장치가 없으면 갱신 시점이 사람 기억에만 달린다.

## 5. 이 저장소의 셋

`scripts/` 의 파일 셋이 위 기준의 서로 다른 자리에 있다.

| 스크립트 | 생성물 | 커밋 | 원본 위치 | 게이트 |
|----------|--------|------|-----------|--------|
| `dump_openapi.py` | `static/js/generated/api.ts` | 함 | 저장소 안 (FastAPI 라우트) | CI 재생성 후 `git diff --exit-code` |
| `snapshot_os_eol.py` | `mappers/os_eol_catalog.json` | 함 | 저장소 밖 (endoflife.date) | 없음 |
| `screenshot.mjs` | PNG | 안 함 | 해당 없음 | 해당 없음 |

첫째는 3절 조건 넷을 다 만족한다. 커밋하지 않으면 wheel 빌드와 이미지 빌드 양쪽에 node 툴체인이 필요해지고, 생성이 결정적이라 대조가 되며, PR diff 에 어떤 스키마 필드가 사라졌는지가 드러난다. 체인의 단계와 규약은 `docs/reference/web/type-contract.md` 가 갖는다.

둘째는 폐쇄망 대응이다. 고객사 내부망에서 런타임 외부 호출이 0 이어야 하므로 EOL 날짜를 미리 긁어 카탈로그로 박는다. 네트워크 말고도 이유가 있다 — 외부 서비스가 죽거나 스키마를 바꾸면 그게 우리 화면 장애가 되고, 같은 이미지가 언제 돌든 같은 판정을 내야 한다.

4절대로 둘째에는 게이트가 없다. 기준 시점 실측으로 카탈로그의 213개 cycle 중 186개가 이미 지난 날짜이고, 마지막 갱신은 2026-07-11 커밋이다.

## 6. 소비자가 사람이 아닌 도구

`screenshot.mjs` 는 렌더된 페이지를 headless chromium 으로 찍고 콘솔 에러도 함께 수집한다. 소비자가 코딩 에이전트이고 사람 워크플로에는 진입점이 없다.

이 성질이 바꾸는 것은 위치가 아니라 셋이다.

- 유지 책임 — 사람이 안 쓰니 낡아도 아무도 안 알아챈다. 게이트도 없다
- 의존성 비용 — 캡처 라이브러리가 저장소 devDependency 면 워크플로와 다른 개발자도 받는다
- 발견 가능성 — 개발 시점 도구 디렉토리에 있으면 사람이 쓰는 도구처럼 보인다

셋 다 파일을 다른 디렉토리로 옮겨서는 안 풀린다. 배치 축이 실행 시점인데 소비자 축을 섞으면 기준이 둘이 되기도 한다. 그래서 옮기지 않고 헤더에 소비자를 명시하는 쪽으로 두었다.

의존성은 저장소 공용으로 남겼다. 쓸 때만 설치하면 안 쓰는 쪽이 비용을 안 지지만 매번 매니페스트와 lockfile 을 건드렸다 되돌려야 한다. 그 손이 안 쓰는 사람이 한 번 받는 비용보다 크다는 판단이다.
