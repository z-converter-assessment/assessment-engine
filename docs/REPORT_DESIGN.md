# 보고서 설계

## 현재 구현을 미루는 이유

보고서는 **진단 로직(diagnostics)** 의 출력을 시각화하는 문서다.
현재 **진단** 로직이 없는 상태이므로, 보고서에 담을 핵심 내용(진단 결과·권고사항)이 존재하지 않는다.

지금 보고서 템플릿을 만들면 수집한 raw 데이터를 나열하는 수준에 그친다.
진단 로직이 정의된 후 보고서 구조를 설계해야 의미 있는 형식이 나온다.

---

## Jinja2 기반 보고서 가능 형식

현재 프로젝트는 이미 Jinja2 SSR 환경이 구성되어 있다(`web/templates/`).
별도 라이브러리 없이 HTML 보고서를 렌더링할 수 있고, PDF는 브라우저 인쇄 기능으로 변환 가능하다.

### 형식 1: HTML 보고서 (브라우저 렌더링)

추가 의존성 없음. 기존 `base.html`을 상속해 보고서 전용 레이아웃을 만든다.
브라우저에서 인쇄(Ctrl+P) → PDF 저장으로 배포 가능.

```
web/templates/
  reports/
    base_report.html   ← 보고서 전용 레이아웃 (헤더·푸터·인쇄 CSS)
    inventory.html     ← 인벤토리 요약
    performance.html   ← 성능 요약
    diagnostic.html    ← 진단 결과 (구현 보류)
```

**적합한 경우**: 담당자가 브라우저에서 열람하거나 PDF로 저장해 공유하는 시나리오.
B2B 내부 포털 성격에 가장 자연스러운 형식.

---

### 형식 2: PDF 직접 생성 (WeasyPrint)

`WeasyPrint` 라이브러리가 Jinja2 렌더링 결과(HTML)를 서버 측에서 PDF로 변환한다.
API 엔드포인트(`GET /api/v1/servers/{id}/report.pdf`)로 PDF를 직접 다운로드할 수 있다.

**추가 의존성**: `weasyprint` (시스템 레벨 cairo·pango 의존성 존재)
**적합한 경우**: 자동화된 보고서 발송, 인쇄 품질 보장이 필요한 경우.
현재 규모에서는 브라우저 인쇄로 대체 가능하므로 도입 우선순위 낮음.

## 우리 프로젝트에 맞는 보고서 종류

진단 로직 구현 전 지금 당장 만들 수 있는 것과, 이후에 만들어야 할 것을 구분한다.

### 즉시 구현 가능

| 보고서 | 내용 | 데이터 출처 |
|--------|------|------------|
| 인벤토리 요약 | 전체 서버 목록, OS·CPU·메모리 스펙 | `server_inventory` |
| 성능 요약 | 기간별 CPU·메모리·디스크·네트워크 평균/최대 | `server_metrics` 집계 |

### 진단 로직 구현 후

| 보고서 | 내용 |
|--------|------|
| 진단 보고서 | 이상 감지 결과, 권고사항, 위험 등급 |
| 이행 보고서 | 클라우드 마이그레이션 적합성 평가 결과 |

## 현재 구현의 한계

### 시계열 차트 인쇄 불가

`chart.html`은 인쇄 대상에서 제외한다. 이유는 두 가지다.

- **Canvas 렌더링**: Chart.js는 `<canvas>`에 그리므로 브라우저 인쇄 시 비트맵으로 캡처된다. 해상도가 낮거나 빈 영역으로 출력될 수 있다.
- **시점 의존성**: 차트는 현재 시점의 시계열을 표시한다. 보고서는 특정 기간의 확정된 스냅샷이어야 하는데, 인쇄 시점에 따라 내용이 달라지는 차트는 보고서 용도에 맞지 않는다.

차트를 보고서에 포함하려면 분석 기간을 확정하고 해당 기간의 피크·평균값을 테이블로 집계하는 별도 뷰가 필요하다. 이는 진단 로직 구현 이후의 작업이다.

### 실시간 메트릭의 출력 시점 의존성

`detail.html`의 실시간 메트릭(CPU·메모리·Disk I/O·Network I/O)은 AJAX로 로드된 현재 시점의 값이다. 인쇄 시 DOM에 렌더링된 값이 그대로 출력되므로, 페이지를 열어둔 시점에 따라 수치가 달라진다. 고정된 분석 시점의 보고서가 필요하다면 별도 스냅샷 API를 활용해야 한다.
