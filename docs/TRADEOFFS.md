# 설계 트레이드오프

프로젝트를 진행하면서 명시적으로 선택한 트레이드오프를 기록한다.
대안이 없어서가 아니라, 현재 스케일과 요구사항 기준으로 의도적으로 선택한 결정들이다.

---

## 1. 멱등성(Idempotency): at-most-once

### 선택한 구조
Redis `SET NX`로 중복 제거 키를 설정한 뒤 DB에 커밋한다.

```
SET idempotent:{message_id} NX  →  DB 커밋
```

### 트레이드오프
SET NX 이후 DB 커밋 이전에 프로세스가 죽으면, RabbitMQ가 unacked 메시지를 재전송하더라도 Redis에 키가 남아있어 중복으로 판단 → 조용히 ack 후 드롭된다. **데이터 유실(at-most-once)** 가능성이 있다.

### 반대 방향의 리스크
순서를 뒤집어 DB 커밋 후 SET NX를 하면 **at-least-once** 가 된다. 같은 메트릭이 두 번 삽입되면 두 시점의 delta 계산이 오염되어 CPU/IOPS/kBps 수치가 왜곡된다. 메트릭 특성상 중복 삽입이 데이터 유실보다 더 해롭다.

### 수용 근거
- 메트릭은 60초마다 재발행되므로 한 샘플 유실은 차트에서 짧은 gap으로 표시될 뿐이다.
- 프로세스가 SET NX와 DB 커밋 사이에 정확히 죽는 확률은 매우 낮다.

## 2. RabbitMQ 큐 TTL: 메시지 유형별 차등

### 선택한 구조
| 큐 | TTL |
|----|-----|
| `server.inventory` | 없음 |
| `server.metrics` | 60초 |
| `server.error` | 60초 |

### 트레이드오프
inventory TTL을 제거하면 컨슈머가 장기간 다운되었다 복구될 때 오래된 인벤토리 메시지가 처리된다. 내용은 upsert이므로 중복 처리 자체는 무해하다.

metrics/error에 60초 TTL을 유지하면 컨슈머 다운 중 쌓인 메트릭은 전부 DLQ로 빠진다. **수집 공백이 발생**하지만, 낡은 메트릭을 뒤늦게 삽입하면 시계열 연속성이 깨지는 부작용이 더 크다.

### 수용 근거
- inventory는 기동 시 1회만 발행되는 one-shot 메시지다. TTL 소실 시 에이전트를 재시작하기 전까지 복구 방법이 없다.
- metrics는 주기적으로 재발행되므로 컨슈머 복구 후 자연스럽게 재개된다.

---

## 3. Redis: 메시지 처리 critical path 포함

### 선택한 구조
멱등성 체크(`SET NX`)가 RabbitMQ 메시지 처리 흐름 안에 있다. Redis 장애 시 예외가 발생하고 메시지는 nack → DLX → DLQ로 이동한다.

### 트레이드오프
Redis 장애 = 모든 메시지 DLQ행. 멱등성 체크를 fail-open(Redis 장애 시 체크 생략 후 처리 계속)으로 바꾸면 Redis 장애 중에도 메시지는 처리되지만, 동일 메시지 중복 처리 가능성이 생긴다.

### 수용 근거
Redis는 캐시, PUB/SUB, 온라인 TTL로 이미 hard dependency다. Redis 장애 시 웹 UI 자체가 정상 동작하지 않으므로, 멱등성 때문에 새로운 단일 장애점이 추가되는 구조가 아니다.

---

## 4. 미등록 서버의 메트릭 드롭

### 선택한 구조
metrics 메시지 수신 시 `machine_id`로 서버를 조회하고, 미등록이면 메트릭을 조용히 드롭한다.

### 트레이드오프
inventory 메시지가 처리되기 전에 metrics 메시지가 도달하면(레이스 컨디션, 또는 inventory가 DLQ로 빠진 경우) 메트릭이 유실된다.

### 수용 근거
- 에이전트가 계속 메트릭을 발행하므로 inventory 등록 후 다음 주기(최대 60초)부터 자동으로 수집된다.
- 미등록 서버의 메트릭을 임시 저장하는 구조는 孤兒 데이터 관리 복잡도를 높인다.

## 5. counter reset 처리: delta < 0 → None

### 선택한 구조
두 시점의 raw 누적값 차(delta)가 음수이면 `None`으로 처리하고 UI에서 "—"로 표시한다.

### 트레이드오프
에이전트 재시작·재부팅 시 카운터가 0으로 리셋되어 delta가 음수가 된다. 이 시점의 데이터는 표시되지 않는다. `boot_time` 기반으로 카운터 리셋 시점을 감지해 해당 샘플만 건너뛰는 방식이 더 정확하지만, 구현되어 있지 않다.

### 수용 근거
재부팅·재시작은 드문 이벤트고, 해당 구간만 "—"로 표시되는 것이 잘못된 수치를 보여주는 것보다 낫다.

---

## 6. 차트 dimension 필터: CAST(:dim AS text) IS NULL 패턴

### 선택한 구조
차트 SQL에서 dimension 파라미터가 None일 때 전체 조회, 값이 있으면 해당 dimension만 필터링하는 단일 쿼리를 유지한다.

```sql
AND (CAST(:dim AS text) IS NULL OR device = :dim)
```

### 트레이드오프
dimension 유무에 따라 쿼리를 분기하면(None이면 WHERE 절 생략, 아니면 포함) 각 쿼리가 더 단순해지고 인덱스 플래너가 최적화할 여지가 생긴다. 단일 쿼리는 코드 중복을 줄이지만 `:dim IS NULL` 분기가 쿼리 플랜에 반영되지 않을 수 있다.

### 수용 근거
현 데이터 규모(서버 수십 대)에서는 성능 차이가 없다. `:dim::text IS NULL` 형태는 SQLAlchemy + asyncpg에서 named parameter 뒤 `::` 파싱 버그가 있으므로 `CAST(:dim AS text)` 로 우회했다.

## 7. SSE 브로드캐스트: 전체 구독 후 서버별 필터링

### 선택한 구조
`metrics.events` Redis 채널을 모든 SSE 연결이 구독하고, 브라우저로 전달할 이벤트는 서버 측에서 `server_id` 일치 여부로 필터링한다.

### 트레이드오프
서버 수가 많고 동시 브라우저 접속이 많으면, 각 SSE 연결이 관련 없는 이벤트를 대량으로 수신하고 버리게 된다. 서버별 채널(`metrics.events.{server_id}`)로 분리하면 불필요한 이벤트를 수신하지 않지만, 채널 수가 서버 수에 비례하여 늘어난다.

### 수용 근거
B2B 내부 포털 특성상 동시 접속자 수가 적고, 서버 수도 수백 대 이하로 예상된다. 단일 채널 구조가 단순하고 Redis 채널 관리 오버헤드가 없다.

## 8. DEV 환경 스키마 관리: web lifespan → consumer depends_on

### 선택한 구조
web 컨테이너 lifespan에서 `CREATE EXTENSION + create_all + create_hypertable`을 수행하고, consumer가 `depends_on web: condition: service_healthy`로 web 헬스체크 통과 후 기동한다.

### 트레이드오프
개발 환경에서는 `docker compose up` 한 번으로 스키마까지 자동 구성되어 편리하다. 그러나 web 재시작마다 lifespan이 실행되고, 프로덕션에서는 web과 DB 마이그레이션 책임이 뒤섞이는 구조가 된다. Alembic 마이그레이션과 함께 사용하면 충돌 위험이 있다.

### 수용 근거
프로토타입~초기 개발 단계에서 별도 마이그레이션 도구 없이 빠르게 스키마를 유지할 수 있다. `create_all`은 이미 존재하는 테이블을 건드리지 않으므로 데이터 유실 위험은 없다. 프로덕션 전환 시 Alembic으로 대체하고 이 의존성을 제거하는 것이 전제된 설계다.

## 9. 캐시 전략: read-through + consumer DEL

### 선택한 구조
consumer가 새 메트릭을 저장한 후 캐시를 직접 갱신하지 않고 `DEL cache:metrics:{id}`만 수행한다. 다음 Web 요청 때 캐시 미스 → DB 조회 → 캐시 SET이 일어난다.

### 트레이드오프
write-through(consumer가 저장과 동시에 캐시도 갱신)라면 저장 직후 첫 요청도 캐시를 타지만, consumer가 Web 서비스 계층의 직렬화 로직을 알아야 하므로 계층 결합도가 높아진다. DEL 방식은 계층을 분리하되, 메트릭 저장 직후 첫 요청은 반드시 DB를 타는 구조다.

### 수용 근거
메트릭은 60초 주기로 갱신되고, SSE 이벤트 수신 후 브라우저가 AJAX를 한 번만 재요청하므로 캐시 미스는 메트릭 저장 직후 1회뿐이다. 계층 분리의 이점이 이 비용보다 크다.

## 10. SSR + AJAX 하이브리드

### 선택한 구조
페이지 초기 렌더링은 SSR(Jinja2)로 제공하고, 메트릭 수치(CPU%·mem% 등)는 별도 AJAX 요청으로 로드한다.

### 트레이드오프
Full SSR이면 매 페이지 요청마다 느린 메트릭 집계 쿼리를 블로킹으로 처리해야 한다. SPA(Single Page Application)면 초기 렌더링이 느리고 클라이언트 라우팅 구현이 필요하다. 하이브리드는 두 방향의 단점을 절충하지만, SSR 페이지와 API 엔드포인트를 이중으로 유지해야 한다.

### 수용 근거
SSE 기반 실시간 갱신은 AJAX 패턴이어야 자연스럽게 구현된다. 인벤토리 정적 정보는 SSR로 빠르게 표시하고, 메트릭은 비동기로 채워 넣는 구조가 사용자 체감 속도와 실시간성을 모두 확보한다.

## 11. inventory 수신 시 online 즉시 마킹

### 선택한 구조
`make_inventory_handler()`에서 upsert 성공 후 `SET online:{server_id} EX 90`을 수행한다. 실제 메트릭이 아직 수신되지 않은 상태에서도 서버가 온라인으로 표시된다.

### 트레이드오프
첫 메트릭 수신까지 최대 60초가 걸리므로, 그 사이 온라인 뱃지가 "에이전트가 살아있다"는 의미보다 "등록됐다"는 의미로 오해될 수 있다. 반대로 inventory 수신 후 online 마킹을 하지 않으면, 서버가 DB에는 등록됐지만 첫 메트릭 수신 전까지 offline으로 표시되어 혼란을 줄 수 있다.

### 수용 근거
inventory를 발행한 에이전트는 직후 60초 안에 metrics를 발행하므로, online 상태의 오표시 구간이 짧다. 등록 즉시 피드백을 주는 것이 UX상 더 낫다.
