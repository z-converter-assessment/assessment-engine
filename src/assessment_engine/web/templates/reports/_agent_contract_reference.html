에이전트-엔진 데이터 계약 (wire 스키마)

에이전트(원격 호스트 설치형, C 언어 — Linux 정적 바이너리 · Windows PE)가 RabbitMQ 로 발행하는 메시지 형식. 정본 스키마는 별도 agent repo schema/wire.schema.json(JSON Schema)·schema/metric-vocab.json(어휘 정본, CI 드리프트 검증) — 엔진 쪽 사람이 읽는 카탈로그는 docs/reference/contracts/agent-data.md(전체 384행 — envelope·메시지별 required 매트릭스· metric 카탈로그·USE 매핑까지). 본 절은 그 핵심만 발췌한다.

안정키 정책 (device 식별)

디스크·네트워크 시계열은 major/minor·인터페이스명 같은 휘발성 식별자 대신 안정키를 쓴다 — 디스크는 dm-uuid → partuuid → wwid → serial → by-id → by-path → name 폴백 체인, 네트워크는 MAC 주소. 물리 disk(type=disk)·물리 iface(kind in physical/bond_master)만 시계열 집계에 포함해 LVM/RAID/crypt·가상 브리지의 이중집계를 배제한다(ADR 0054 5항).

각 필드가 실제로 무슨 함수·정보원을 통해 수집되는지 — 별도 agent repo(src/ Linux, windows-agent/src/ Windows) 소스 코드 기준. Windows 는 WMI 를 전혀 쓰지 않는다 — perflib raw 카운터(RegQueryValueExA(HKEY_PERFORMANCE_DATA)) · Native API(NtQuerySystemInformation) · IOCTL · 레지스트리를 직접 호출한다.

Assessment API 계약 (GET /api/assessment)

재해복구/마이그레이션 에이전트가 타겟 VM 을 재현(소스 레이아웃 그대로) 또는 수정 사이징(관측 부하 맞춤)으로 생성하는 데 필요한 것을 한 응답으로 반환하는 외부 연동 계약. 정본은 docs/reference/contracts/assessment-api.md(538행) — 파라미터 전체·JSON 예시·엣지 케이스는 거기서 확인. 본 절은 설계 원칙과 사이징 모델만 요약한다.

설계 원칙

  • 안전 > 정확 > 절감 — 과소 사이징(대상이 부하를 못 받는 상황)을 절대 만들지 않는 게 최우선. 셋이 충돌하면 항상 안전이 이긴다.
  • 플랫폼 중립 — vCPU·MiB·GiB 같은 원시 수량으로 응답, 특정 하이퍼바이저·클라우드 SKU 이름에 묶이지 않는다.
  • 재현 범위 — 레이아웃 청사진(OS·스토리지·네트워크 구성)까지만. 데이터 이관 자체는 계약 범위 밖.
  • 계약 규약(never-change) — contract_version(major.minor)은 additive-only. 필드 추가는 minor, 구조 파괴는 major(현 1.0). 소비자는 모르는 axis 를 max(current, recommended)로, 모르는 enum 을 미상/보수적 등급으로 처리해야 한다(하위 호환 의무).

응답 구조 (서버 항목 5계층)

계층내용
identityhostname·public_id·온라인 상태 — 소비자가 자기 인벤토리와 매칭하는 키.
reproductionOS·부팅·네트워크·스토리지(block_devices 트리 + lvm_vgs + mounts) — 소스 레이아웃 그대로 재현하기 위한 팩트.
sizing자기서술 axes[] 배열(cpu/memory 호스트 1축 + disk 마운트별 N축) — current/recommended/action/estimate_quality.
assessmentclassification/confidence/data_quality — right-sizing 판정 결과.
diagnosticsroot_cause·자원별 상태·advisory — 선택 소비(파싱 안 해도 sizing 계약은 완결).

사이징 모델

  • CPU 는 p95(탄력 자원 — 순간 초과를 실행 큐로 흡수), 메모리는 near-peak(5분 버킷 max 의 p99.9 — 비탄력 자원, 평균 기반은 실제 최대 상주치를 과소평가해 OOM 위험).
  • 디스크는 마운트별(per-mount) 사이징 — host-worst 단일값 폐기, 절대 축소하지 않음(never-shrink).
  • 자원별 독립 처방 — 근본원인(diagnostics.root_cause)은 메타 정보로만 노출하고 sizing.axes 는 인과와 무관하게 관측된 부족 전부를 반영한다. 1회성 마이그레이션 산출이라 재평가 루프가 없어, 인과 추정을 믿고 억제하면 틀렸을 때 과소 사이징으로 흐른다 — 이 원칙을 보고서·/api/right-sizing에도 동일 적용(아래 "분류 기준" 절).
