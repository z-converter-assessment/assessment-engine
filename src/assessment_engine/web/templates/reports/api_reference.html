자원 적정성 판정 API — 상세 사용법

서버별 CPU·메모리·디스크 3축 사이징 판정 + 네트워크 품질을 파싱 쉬운 JSON 으로 반환한다. 화면(보고서·자원 평가)과 동일 산식이라 값이 정합한다. "이렇게 프로비저닝하면 된다"를 자동화가 바로 소비하도록 설계했다. 외부 시스템은 내부 식별자(public_id)를 모르는 게 보통이라, 자기 인벤토리가 아는 hostname·ip 로 조회한다(public_id 를 알면 그걸로 유일 지정 가능).

GET /api/right-sizing

파라미터

이름타입기본값설명
hostnamestring전체쉼표 구분 호스트명(정확 매칭, 대소문자 구분).
ipstring전체쉼표 구분 IPv4(물리 인터페이스 정확 매칭).
public_idstring (UUID)전체쉼표 구분 서버 public_id. 유일 키 — 안전(중복 없음).
pairstring없음쉼표 구분 순서쌍 hostname~discriminator (discriminator = IP 또는 public_id). 호스트명 중복 시 정확 지정.
window_daysinteger (1–30)14평가 윈도우(일). 자원 적정성 표준 창.
endstring (ISO 8601)현재윈도우 종료 시각(tz-aware 권장).

hostname·ip·public_id·pair 중 하나라도 매칭되면 포함(OR 결합). 전부 미지정이면 전체 서버(1대·N대·전체 동일 엔드포인트).

호스트명 중복 안전 (파싱 전 필독)

hostname 은 유일하지 않다 — 유일 안전키는 public_id(UUID) 뿐이다. 매칭은 대소문자를 구분한다 (web-01 과 WEB-01 은 다른 값).

  • 같은 호스트명이 2대 이상이면 hostname=web-01 은 그 전부를 반환한다.
  • 정확히 한 대만 지정: 순서쌍 pair=web-01~10.0.0.5 또는 pair=web-01~<uuid> — host AND 판별자(IP 또는 public_id)를 동시에 만족하는 서버만 매칭한다.
  • 서버가 충돌을 검사해 반환하는 안전 신호:
    • servers[].hostname_ambiguous — 그 호스트명이 환경 내 2대 이상 공유(true 면 hostname 단독 사용 위험).
    • warnings.ambiguous_hostnames — plain hostname 필터가 중복명을 명중(pair/public_id 권장).
    • warnings.unresolved_pairs — 어떤 서버로도 해석 안 된 순서쌍(오타·불일치).

사용 예

GET /api/right-sizing                                         # 전체 서버
GET /api/right-sizing?public_id=<uuid>                        # 1대 (public_id)
GET /api/right-sizing?hostname=web-01,db-03                   # N대 (호스트명)
GET /api/right-sizing?ip=10.0.0.5,10.0.0.6                    # N대 (IP)
GET /api/right-sizing?pair=web-01~10.0.0.5                    # 중복 호스트명 정확 지정 (host AND IP)
GET /api/right-sizing?pair=web-01~<uuid>                      # 중복 호스트명 정확 지정 (host AND public_id)
GET /api/right-sizing?window_days=7&end=2026-07-01T00:00:00Z  # 창·기준 시각 지정

종합 권고(recommendation) 포맷 — 파싱 규칙

프로비저닝 결정은 recommendation.actions 만 파싱한다. per-resource sizing_target_* 는 각 자원을 독립 가정한 진단값이라, 인과 결합(예: 메모리 포화가 CPU·디스크 I/O 를 유발) 시 증상 자원도 목표를 갖는다 — 그대로 증설하면 잘못이다. actions 는 근본원인만 담고 증상은 suppressed 로 분리한다.

recommendation 객체 구조:

필드타입값 | 의미
summarystring사람용 요약(예 메모리 -> 24GB). 표시 전용 — 파싱하지 말 것.
kindstring5개: provision(증설) | downsize(축소) | decommission(종료·통합) | maintain(적정) | insufficient(표본 부족).
actions[]object[]실제 조치 — 근본원인 자원만(증상 제외). 빈 배열이면 조치 없음(maintain·insufficient, 또는 다운사이즈 게이트 미충족 관찰만).
actions[].resourcestring5개: cpu | memory | disk_capacity | disk_io | network.
actions[].opstring3개: increase(cpu·memory·disk_capacity 증설) | tier_up(disk_io 티어 상향) | decrease(과다 축소).
actions[].target_cores / target_mb / target_gbinteger목표 총량(자원 타입별 키). 수치 미상(포화 주도·티어 상향)이면 키 없음.
actions[].target_displaystring사람용 표시(예 메모리 -> 24GB·디스크 티어 상향).
suppressed[]string[]증상 자원 kind — 근본원인 해결 후 재평가. 독립 조치 금지. 없으면 [].

파싱 예: kind 로 방향 결정 -> actions[] 순회하며 resource + target_cores/_mb/_gb 로 자원별 목표 총량 적용. suppressed 자원은 건드리지 않는다. (예: 메모리 근본원인이면 actions=[{memory, target_mb}], suppressed=["cpu","disk_io"] — 메모리만 증설.)

null | '—' 표기 규약

JSON null = 해당 값이 없거나 아직 측정되지 않음(N/A). 즉 필드의 원래 타입(number·string·integer·boolean)에 null 이 허용된다는 뜻이다. 화면(보고서·표)에서는 이 null 이 —(대시)로 표시된다 — — = null = "값 없음/미측정"으로 동일하다. 위 표의 "null: 예"인 필드만 null 이 올 수 있다. saturation·signal 객체 안 measured=false 이면 그 축 값(value·saturated·exceeded)은 null 이다.
