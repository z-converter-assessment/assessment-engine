보고서 용어·개념 정리

환경·서버 보고서 본문에 등장하는 핵심 키워드·분류 기준의 정의. 임계값·판정 순서 상세는 아래 절 참조.

키워드 정의
자원 적정성 평가관측 부하 대비 할당 자원의 적정성을 자원 적정성 5 상태(자원 부족·과다·유휴·정상·표본 부족)로 판정해 권고. 분류 기준은 아래 "분류 기준" 절.
USE MethodBrendan Gregg 의 자원 진단 프레임 — Utilization(이용률)·Saturation(포화)·Errors 세 축. 본 보고서는 Utilization·Saturation 두 축 적용.
평균 (avg)윈도우 안 모든 시점값의 산술 평균. 정상 부하의 중심 경향.
p95작은 값부터 정렬해 95% 위치의 값 — 상위 5%(일시 spike)만 초과. 분류 1차 입력. 평균보다 클 수 있음(분포 우측 꼬리).
peak윈도우 안 시점별 최댓값. 실제 관측 burst 강도.
변동성peak / p95 비율 — 클수록 burst 부하. 임계·용도는 "엔지니어 보조 지표" 절.
Saturation (포화)자원이 처리 한계를 넘어 대기열이 쌓이는 신호 — CPU run queue(Linux procs_running · Windows Processor Queue Length)·메모리 페이징(Linux swap page-out · Windows Pages Input/sec 하드폴트)·디스크 I/O await(양 OS, Windows 는 IOCTL). 발생 시 이용률이 낮아도 증설 신호. 네트워크 혼잡(재전송·드롭·conntrack)은 별도 품질 플래그(사이징 아님).
서비스 분류호스트 구동 워크로드를 카테고리(web·db·cache·container 등)로 분류 — 서비스 이름·실행 파일·listen 포트 신호 종합. container 등 런타임 스택은 호스트당 1로 카운트.
메모리 구성전체 메모리 대비 used(사용)·available(가용)·cached(페이지 캐시)·buffers(버퍼) 윈도우 평균 비율. cached/buffers 는 회수 가능 영역이라 available 에 포함.
CPU 분류CPU 시간을 user(응용)·system(커널)·iowait(디스크 대기) 로 분해한 윈도우 평균 비율. iowait 높으면 디스크 병목.
OS EOLOS 배포판·버전의 vendor 지원 종료일(endoflife.date 기준). 임박·경과 시 보안 패치 중단 — 마이그레이션 선행 필요.
운영 신호자원 적정성 평가와 별도의 안정성 신호 — 데이터 수집 끊김(gap)·OS 지원 종료·에이전트 재시작·재부팅 빈도. 분류 정상이어도 발화 시 운영 조치 선행.
신뢰도분류 결과의 확신 수준 단서 — 미관측 축·표본 부족 시 노출. 분류 자체는 가진 데이터로 완결. 상세는 "신뢰도 단서" 절.
평가 윈도우통계 산출 기간 — 보고서 표준 14일. 상세는 "평가 윈도우" 절.

분류 기준

환경·서버 보고서의 자원 적정성 평가는 recommendation 모듈 단일 진실로 결정. 아래 표의 임계값을 USE Method (Brendan Gregg) Utilization·Saturation 두 축으로 적용해 5 상태 (자원 부족 under_provisioned / 과다 할당 over_provisioned / 유휴 idle / 정상 optimal / 표본 부족 insufficient_data) 산출. 조치(증설·축소·종료·통합)는 상태에서 파생. 임계 출처는 AWS Compute Optimizer · Azure Advisor · GCP Recommender · Kleinrock 등 산업 표준 종합.

자원별 판정 — 입력·임계·사이징 (엄밀)

자원 5축을 각각 독립 판정(assess_*)한 뒤 호스트로 종합(rollup_host). 아래는 자원별 입력 신호·판정 임계·출처와 사이징 산식. CPU·메모리는 목표 사양(코어/GB)을 산출하고, 디스크 용량은 목표 GB, 디스크 I/O·네트워크는 사이징 대상이 아니라 상태만 판정한다. 모든 임계는 recommendation 모듈 상수 단일 진실 (재계산 0 — 화면·API·보고서 동일 값).

판정 순서

신호를 모아 판정한다: 자원(CPU·메모리·디스크)마다 관측된 축을 근거로 삼는다. 자원 부족 (under_provisioned) 은 위험 신호가 하나라도 걸리면 발화하고(OR — 누락 0), 걸린 신호를 근거(triggers)로 권고에 노출한다. 과다 할당 (over_provisioned) 은 CPU·메모리가 둘 다 다운사이즈 임계 아래일 때만 잡는다(AND — 보수적). 포화 축을 못 본 서버를 과다 할당으로 단정하지 않는다.

OS 분기 (Windows): 세 포화 축은 OS마다 다른 실측 신호로 재는다 (분류 체계·임계 도메인은 같고 신호원만 다르다). CPU 포화는 Linux 실행 큐(procs_running/cores >= 1.0)·Windows Processor Queue Length(run queue/cores >= 2.0). 메모리 포화는 Linux swap page-out(여유 RAM 에도 상시 baseline 인 Windows pagefile 사용량은 신호 아님)·Windows Memory\Pages Input/sec rate p95(>= 20, 하드 페이지 폴트율 — mmap 소프트폴트 미혼입). 디스크 I/O 포화는 양 OS 공통 await_p95 > 20ms — Windows 는 IOCTL_DISK_PERFORMANCE 의 ReadTime/WriteTime(100ns) 누적으로 await 를 산출하고, IOCTL 미부착 구세대 viostor 만 Avg Disk Queue Length(디스크당 >= 2)로 폴백한다. 각 축은 해당 카운터를 못 읽거나 미부착이면 그 축만 미관측으로 기록된다("포화 수치 미관측" confidence 단서). 분류는 utilization·capacity·측정된 포화 축으로 완결되며 "표본 부족"이 아니다 — cpu_p95·mem_p95 가 산출되기 때문.

순위 분류 조건
1자원 부족 (under_provisioned)위험 신호 OR (하나라도): cpu_p95>=70% / mem_p95>=90% / 디스크 용량(소진 30일 이내 or 정적 85% or inode 소진) / CPU 포화(Linux procs_running/cores>=1.0 · Windows Processor Queue/cores>=2.0) / 디스크 I/O await>20ms(양 OS, 구세대 viostor 만 disk queue>=2) / 메모리 페이징(Linux swap page-out · Windows Pages Input/sec p95>=20). 유휴 보다 우선 — CPU 가 낮아도 압박 신호가 있으면 미사용이 아니라 자원 부족.
2유휴 (idle)활동 3축 전부 quiescent — cpu_p95 <= 3% AND net <= 2 Mbps AND 디스크 baseline IOPS <= 5 (위험 신호 0). 하나라도 활동 있으면 유휴 아님(정상/과다로).
3표본 부족 (insufficient_data)cpu_p95·mem_p95 둘 다 null + under 신호 없음 (평가 데이터 없음)
4과다 할당 (over_provisioned)CPU 또는 메모리를 이용률 70% 목표로 다운사이즈 가능 — 필요 사양(ceil(현재 * p95 / 70)) < 현재. CPU 는 어느 코어든 p95>=85%면 보류(단일스레드 보호). 포화 축을 못 본 서버는 과다로 단정 안 함.
5정상 (optimal)위 모두 미해당 (다운사이즈선 초과, 압박 없음)
—네트워크 혼잡 (orthogonal)위 분류와 독립 — 재전송>1% or 드롭>0.5% or conntrack>=80%면 품질 경고 플래그. 사이징(증설·축소) 결정에 영향 없음.

호스트 종합 — 근본원인 (인과)

자원별 부족을 호스트로 종합할 때 인과 상류를 짚어 root 만 처방하고 하류(증상)는 억제한다 — 삼중 처방 방지. 인과 사슬: 메모리 -> 디스크 I/O -> CPU. "근본원인" 칼럼·권고가 이 종합과 정합.

패턴판별근본원인 / 처방
메모리발메모리 페이징 발생 AND 동반 디스크 I/O 또는 CPU 부족root = 메모리. 디스크 I/O·CPU 는 swap 트래픽·대기의 증상 -> 처방 억제. 표시 "메모리 (CPU·디스크 I/O 유발)"
디스크발디스크 I/O 병목 AND CPU 부족 AND procs_blocked(D-state) p95 >= 1.0root = 디스크 I/O. CPU 로드는 D-state 블록의 증상. 표시 "디스크 I/O (CPU 유발)"
독립 부족결합 신호 없음각자 처방 (root = 최상류 memory > cpu > disk_io > disk_capacity). 표시 "CPU·디스크 I/O"(나열, 인과 함의 없음)

신뢰도 단서

분류는 가진 데이터로 완결하고, 확신을 떨어뜨리는 요인은 별도 단서로만 노출 — 보고서 "신뢰도" 칼럼·환경 자원 평가 "자원 부족" 카드 공통. 비어 있으면 신뢰도 저하 요인 없음.

단서 조건 의미
포화 수치 미관측 (coverage_gap)포화 축 값이 미관측 — 예: Windows 에서 perflib/diskperf 미부착으로 Processor Queue Length·Pages Input/sec·await 중 일부 미발행 (이용률·capacity·측정된 나머지 축은 정상)이용률·capacity·측정된 포화 축으로 분류 완결 — "표본 부족" 아님. 해당 카운터 수집 재개 시 자동 해제.
표본 부족 (low_precision)관측 이력 30h 미만 (14일 창 누적) 또는 버스티(p95/median > 2)이용률·포화 p95 통계 정밀도 저하 — 짧은 관측·수집 공백·큰 변동. 절대 바닥 30h.
상승 추세 (nonstationary)이용률이 하루 0.2%p 이상 상승 추세forward-looking 결정 한정 — 지금 여유 있어도 다운사이즈는 보류(곧 부족 전환 가능).
충실도 편향 (biased)steal p95 >= 5% (하이퍼바이저 vCPU 경합) — virtio 근사 계통표본 늘려도 안 줄어드는 구조 편향. 다운사이즈 게이트 내부용(호스트 신뢰도 노트엔 노이즈라 미표시).

다운사이즈 게이트: 과다 할당(over) 분류는 위 조건이면 늘 뜨지만, 구체적 축소 처방("코어 N개로")은 잘못된 축소가 최악이라 신뢰도가 충족될 때만 낸다 — 정밀·커버리지·충실도 온전 AND 상승 추세 아님 AND 창 대비 관측 비율(sample_sufficiency) 0.7 이상. 문턱은 절대 시간이 아닌 비율이라 창 길이가 바뀌어도 불변.

권고 (분류 -> 조치) — 근거

권고는 분류에서 결정론으로 나온다 — 같은 분류·같은 신호면 늘 같은 문구다(환경 보고서 "조치 필요 호스트"·서버 단일 보고서 "자원 적정성 평가"가 공유, 임계 재계산 0). 세 원칙으로 처방한다.

  • 인과 억제 — 자원 부족은 근본원인만 처방한다. 메모리 포화가 CPU·디스크 I/O 를 끌어올린 경우 "메모리 증설"만 내고 CPU·디스크는 증상이라 억제한다(근본원인 칼럼이 인과를 전달). 같은 병목에 두세 번 처방하는 걸 막는다.
  • 사이징 착지점 — 목표는 이용률 70% 착지가 기본(AWS Compute Optimizer Balanced). 메모리는 부족하면 급격히 무너져 이용률 목표와 "현재+30%" 중 큰 값을 쓴다. 디스크 용량은 현 성장률로 1년 버티는 총량, 디스크 I/O 는 수치 목표 없이 티어를 올린다.
  • 다운사이즈 게이트 — 과다는 분류는 늘 뜨지만 "코어 N개로" 같은 구체 축소는 신뢰도가 온전할 때만 낸다(정밀·커버리지·충실도 온전 + 상승 추세 아님 + 창 대비 관측 0.7 이상). 잘못 줄이는 게 최악이라, 미충족이면 축소는 보류하고 관찰만 권한다.

네트워크 품질 — 사이징과 별개 축 (상세)

네트워크는 자원 적정성(자원 부족·과다·유휴) 분류에 넣지 않는다 — 네트워크 혼잡은 vCPU·RAM 증설·축소로 풀리지 않는(경로·NIC·conntrack 튜닝) 품질 문제라 사이징 처방과 도메인이 다르다. 대신 별도 품질 판정(정상·혼잡·미측정)으로 orthogonal 하게 노출하고 사이징 분류는 그대로 둔다. 신호는 OS 중립 — 리눅스·윈도우 동일 지표.

진단 칼럼 해석

운영 신호 임계

자원 적정성 평가와 별도의 운영 안정성 신호 — 분류가 정상이어도 발화하면 적정성 판정보다 운영 조치가 선행되어야 함. 실시간 현황 페이지 운영 신호 카드에 3종 노출. 보고서는 발행 윈도우 기준이라 전역 신호(gap·에이전트 불안정)는 미표시 — OS EOL 만 표시하고, 재부팅·에이전트 재시작은 윈도우 안 카운트로 세부 서버 목록 시스템 안정성 칼럼에 표시.

평가 윈도우

자원 적정성 평가 표준은 recommendation.WINDOW_DAYS = 14일 (AWS Compute Optimizer 기본 lookback) — 보고서·서버 목록 분류·환경 개요 자원 이용·포화 6도넛·환경 자원 평가가 모두 이 14일 창으로 정합(화면 간 의미 분기 0). 보고서 발행·환경 자원 평가는 15m / 1h / 6h / 24h / 7d / 14d / 30d 구간·앵커 override 가능하며 분류·통계·세부 목록 모두 선택 구간으로 평가. 실시간 현황 페이지만 최신 스냅샷(30초 갱신, 윈도우 아닌 순간값)이고, 서버 상세 차트는 실시간 모니터링이라 별도(기본 15분). 데이터가 14일보다 짧으면 판정은 그대로 완결되고 신뢰도 단서("표본 부족", 30h 미만)가 자동으로 붙는다 — 별도 창 축소 없음. 버킷(집계 단위)은 구간별 자동 결정.
