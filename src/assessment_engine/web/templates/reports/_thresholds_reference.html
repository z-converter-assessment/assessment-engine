보고서 용어·개념 정리

환경·서버 보고서 본문에 등장하는 핵심 키워드·분류 기준의 정의. 임계값·판정 순서 상세는 아래 절 참조.

키워드 정의
Right-sizing관측 부하 대비 할당 자원의 적정성 평가 — 6 분류(리소스 부족·과다·유휴·종료 권장·정상·표본 부족)로 권고. 분류 기준은 아래 "분류 기준" 절.
USE MethodBrendan Gregg 의 자원 진단 프레임 — Utilization(이용률)·Saturation(포화)·Errors 세 축. 본 보고서는 Utilization·Saturation 두 축 적용.
평균 (avg)윈도우 안 모든 시점값의 산술 평균. 정상 부하의 중심 경향.
p95작은 값부터 정렬해 95% 위치의 값 — 상위 5%(일시 spike)만 초과. 분류 1차 입력. 평균보다 클 수 있음(분포 우측 꼬리).
peak윈도우 안 시점별 최댓값. 실제 관측 burst 강도.
변동성peak / p95 비율. 1.5 이상이면 burst 가 커 평균 아닌 peak 기준 sizing 권장.
Saturation (포화)자원이 처리 한계를 넘어 대기열이 쌓이는 신호 — CPU load(run queue)·메모리 swap(page-out)·디스크 iowait. 발생 시 이용률이 낮아도 증설 신호.
서비스 분류호스트 구동 워크로드를 카테고리(web·db·cache·container 등)로 분류 — 서비스 이름·실행 파일·listen 포트 신호 종합. container 등 런타임 스택은 호스트당 1로 카운트.
메모리 구성전체 메모리 대비 used(사용)·available(가용)·cached(페이지 캐시)·buffers(버퍼) 윈도우 평균 비율. cached/buffers 는 회수 가능 영역이라 available 에 포함.
CPU 분류CPU 시간을 user(응용)·system(커널)·iowait(디스크 대기) 로 분해한 윈도우 평균 비율. iowait 높으면 디스크 병목.
OS EOLOS 배포판·버전의 vendor 지원 종료일(endoflife.date 기준). 임박·경과 시 보안 패치 중단 — 마이그레이션 선행 필요.
운영 신호sizing 과 별도의 안정성 신호 — 데이터 수집 끊김(gap)·재부팅 빈도·에이전트 재시작. 분류 정상이어도 발화 시 운영 조치 선행.
평가 윈도우통계 산출 기간 — 표준 7일(recommendation.WINDOW_DAYS). 짧으면 p95 표본 신뢰도 저하.

분류 기준

환경·서버 보고서의 Right-sizing 분류는 recommendation 모듈 단일 진실로 결정. 아래 표의 임계값을 USE Method (Brendan Gregg) Utilization·Saturation 두 축으로 적용해 6 분류 (under_provisioned / over_provisioned / idle / shutdown / optimal / insufficient_data) 산출. 임계 출처는 AWS Compute Optimizer · Azure Advisor · GCP Recommender · Kleinrock 등 산업 표준 종합.

판정 순서

evidence 기반: 자원(CPU/Mem/Disk)별로 가진 축을 신호로 모은다. under_provisioned 는 위험 신호 중 하나라도 hit 되면 발화하고(OR — 누락 0), hit 된 신호를 근거(triggers)로 권고에 노출한다. over_provisioned 는 cpu·mem 이 둘 다 다운사이즈 임계 이하일 때만(AND — 보수적). saturation 못 본 Windows 를 over 로 단정하지 않는다.

OS 분기 (Windows): swap 은 Linux page-out(메모리 압박) 신호이나 Windows pagefile 은 여유 RAM 에도 상시 사용되는 baseline 이라 saturation 신호가 아니다. 따라서 Windows 는 swap 축을 제외하고(swap_used 무시), load(CPU run queue) 는 OS 부재라 미관측 축으로 기록된다. utilization·capacity 로 분류는 완결되며("이용률 기준 평가" confidence 단서), "데이터 부족"이 아니다 — cpu_p95·mem_p95 가 산출되기 때문. 동일 통계라도 Linux 는 load/swap 으로 under, Windows 는 utilization 기준으로 같은 분류 체계 안에서 결론난다. Windows agent 가 등가 카운터(Processor Queue Length 등)를 발행하면 미관측 축이 자동 채워진다.

순위 분류 조건
1under_provisioned위험 신호 OR (하나라도): cpu_p95>=70% / mem_p95>=80% / disk>=85% / (load_15m/cores)>=1.0 / iowait>=20% / swap(Linux). idle/shutdown 보다 우선 — CPU 가 낮아도 압박 신호가 있으면 미사용이 아니라 자원 부족.
2idlecpu_peak <= 1% AND net <= 1 KB/s (위험 신호 0)
3shutdowncpu_p95 <= 3% AND net <= 2 Mbps (위험 신호 0)
4insufficient_datacpu_p95·mem_p95 둘 다 null + under 신호 없음 (평가 데이터 없음)
5over_provisionedcpu_p95 <= 30% AND mem_p95 <= 50% (둘 다 관측·낮음)
6optimal위 모두 미해당

고객 양식 권고

환경 보고서 "조치 필요 호스트"(under/over/idle/shutdown)와 서버 단일 보고서의 "권고" 표시는 mapper _build_recommendation_action 단일 진실. under_provisioned 는 recommendation.assess 가 산출한 hit 신호(triggers)를 mapper 가 증설 권고로 변환·결합 ("/" 구분 — 임계 재계산 없이 assess 단일 소스), 그 외는 분류별 고정 문구. optimal/insufficient_data 는 조치 불필요라 환경 "조치 필요 호스트"엔 미노출, 서버 단일 보고서엔 상태로 표시. 엔지니어 "판단"(원인 진단)과 별도 축으로, 권고는 다음 행동(조치)을 제시한다.

판단 컬럼 해석

엔지니어 양식 "판단" 컬럼은 위 보조 지표를 아래 우선순위로 평가해 가장 시급한 신호 1개를 자동 진단 — 분류 판정 순서와 동일하게 위에서부터 첫 매칭에서 확정 (short-circuit). 분류(sizing 방향)와 별도 축으로, 입력 지표는 겹치나 출력은 원인 해석 문구다.

순위 조건 판단 문구
1swap_used = true메모리 부족 (스왑 발생)
2iowait_p95 >= 20%디스크 I/O 병목
3load_15m / cpu_cores >= 1.0CPU saturation
4mem_p95 >= 80%메모리 압박
5cpu_p95 >= 70%CPU 압박
6cpu 또는 mem 변동성 >= 1.5변동성 큼 (burst)
7cpu_p95 <= 3%거의 미사용
8cpu_p95 <= 30% AND mem_p95 <= 50%여유 있음 (축소 검토)
9위 모두 미해당정상

운영 신호 임계

Right-sizing 분류와 별도의 운영 안정성 신호 — 환경·서버 엔지니어 양식 KPI / 컬럼 / 세부 카드에 노출. 분류 (under/over/optimal) 가 정상이어도 운영 신호가 발화하면 sizing 보다 운영 조치가 선행되어야 함.

신호 정의 임계 근거 / 용도
데이터 수집 끊김 (gap)last_metric_at 부터 경과 분5분 이상 + 24h 안 발생Agent · MQ · DB write 정지 1차 신호 — 메트릭 신뢰도 zero
OS EOLOS distro · version 의 vendor EOL date 매핑 (정적)임박 또는 지남OS vendor 발표 - 보안 패치 중단, 마이그레이션 선행 필요
Agent 불안정 (reboot)윈도우 안 boot_time 변경 횟수3회 이상비정상 재부팅 누적 - sizing 평가 신뢰도 저하

평가 윈도우

평가 윈도우 표준은 recommendation.WINDOW_DAYS = 7일. 대시보드·환경 보고서·서버 보고서 모두 본 상수 참조. 보고서 라우터에 한해 ?time_range=15m / 1h / 6h / 24h / 7d / 14d / 30d override 허용. 윈도우가 너무 짧으면 p95 표본 신뢰도가 낮아짐 — 단기 윈도우 결과는 spike 확인용으로 한정 권장.
